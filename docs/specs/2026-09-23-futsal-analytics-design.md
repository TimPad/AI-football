# AI-football: аналитика футзальных матчей по видео — дизайн

**Дата:** 2026-09-23
**Статус:** черновик на ревью

---

## 1. Цель и рамки

**Продукт.** Загружаешь запись футзального матча со статичной камеры — получаешь физические и позиционные метрики по командам и игрокам: дистанции, скорости, спринты, тепловые карты, компактность.

**Пользователи.** Студенческие и любительские футзальные команды. Первая целевая площадка — зал, где снимается МССИ.

**Горизонт текущего цикла (~3 месяца):** физические метрики и тепловые карты. Дальше — владение и передачи (зависят от трекинга мяча, см. фазу 5), затем события.

**В этот цикл не входят:**
- ТВ-трансляции и движущиеся камеры
- футбол 11×11
- события: удары, отборы, стандарты, xG
- обработка в реальном времени
- автоматическое распознавание номеров на форме

## 2. Входные данные: что известно

Есть две установки камеры, и у каждой свои проблемы:

| | МССИ — целевая | Кострома — полигон |
|---|---|---|
| Источник | VK, нарезка 11 с | YouTube, полный матч 43:48 |
| Разрешение | ~1080p | 1280×720, 25 fps |
| Положение камеры | угол зала, высоко | сбоку, с балкона |
| Оптика | сильная бочкообразная дисторсия | дисторсия слабая |
| Поле в кадре | целиком | ближние ворота за кадром, справа обзор режет занавес |
| Формы | красные против сине-фиолетовых; судья и дальний вратарь **оба в жёлтом** | розовые против зелёно-белых; судьи в чёрном |
| Помехи | многослойная разметка зала, запасные у кромки поля, отражения на паркете | зрители на балконе прямо над полем |

Локально лежит фрагмент Костромы: `data/raw/kostroma_futsal_x-ITNQMFm0M_115-415.mp4` — 300 с, 7500 кадров, с 1:55 исходной записи, камера неподвижна на всём протяжении.

**Главное следствие:** калибровка между установками не переносится. Всё, что зависит от камеры, живёт в конфиге установки (раздел 4.1), а не в коде.

## 3. Исходные замеры (baseline)

Железо: MacBook Pro M2 Pro, 16 ГБ, GPU через MPS, torch 2.14.

### 3.1 Скорость детекции

Оценка для матча: 45 минут записи, обработка с прореживанием до 10 fps (27 000 кадров).

| модель | imgsz | fps | матч 45 мин |
|---|---:|---:|---:|
| yolo11n | 960 | 47.9 | 9 мин |
| yolo11n | 1280 | 50.4 | 9 мин |
| yolo11s | 960 | 52.4 | 9 мин |
| yolo11s | 1280 | 37.4 | 12 мин |
| yolo11m | 960 | 17.1 | 26 мин |
| yolo11m | 1280 | 9.7 | 46 мин |

Для n и s порядок чисел недостоверен: n на 1280 обогнал n на 960, так быть не может. Время здесь съедают накладные расходы, а не вычисления. Цифры для m монотонны, им можно верить. Считается только детекция; сквозной пайплайн с декодированием видео будет медленнее — ориентировочно в 1.3–1.5 раза.

**Вывод:** фазы 1–4 целиком делаются локально, Colab не нужен. Ф5 исследовать локально можно, но инференс по тайлам кадра дороже в разы — для прогона по всем матчам может понадобиться внешний GPU.

### 3.2 Качество детекции людей (yolo11m, 1280)

| момент | conf ≥ 0.10 | conf ≥ 0.25 | ниже линии балкона |
|---|---:|---:|---:|
| t=5 с | 54 | 26 | 10 |
| t=60 с | 42 | 27 | 10 |
| t=150 с | 45 | 26 | 9 |
| t=240 с | 47 | 28 | 7 |

- Отсечка по зоне поля убирает 66% детекций, и это при грубой горизонтальной линии вместо настоящего полигона.
- Внутри поля находится 7–10 человек при ожидаемых ~12. Часть игроков уходит за левый край кадра, часть, возможно, пропущена. Разделить эти случаи можно только на размеченном эталоне (фаза 2).

### 3.3 Мяч (COCO-класс `sports ball`, conf ≥ 0.10)

- найден на 6 кадрах из 150 (4%)
- уверенность: медиана 0.16, максимум 0.25 (на одном кадре вне скана — 0.28)
- размер: медиана 12 px, разброс 9–44 px

Готовая модель мяч практически не видит. Когда мяч крупный и близко к камере — ловит. Это аргумент за собственный детектор, но не гарантия, что тот справится на дальней половине поля.

## 4. Архитектура

Четыре слоя обработки плюс конфиг установки. Слои общаются **только через файлы с фиксированной схемой**:

```
configs/venues/<venue>/        ← один раз на установку камеры
        │
видео ──▶ [L1 detect] ──▶ detections.parquet   пиксели, без идентичности
                │
          [L1 track]  ──▶ tracks.parquet       пиксели + track_id + роль/команда
                │
          [L2 state]  ──▶ state.parquet        метры на поле
                │
          [L3 metrics]──▶ metrics.json
                │
          [L4 service]    API, очередь, хранилище, дашборд
```

**Принципы:**

1. **Каждый артефакт кэшируется на диск.** Детекция — самая дорогая часть, минуты на матч. Трекинг, проекция и метрики — секунды. Если поменялась формула метрики, заново считаются только метрики.
2. **Детекция и трекинг — раздельные шаги.** Поэтому в `detections.parquet` нет `track_id`. Перенастройка трекера не требует повторного прогона детектора.
3. **Каждый шаг запускается отдельно из командной строки** и читает только свой входной артефакт. Это позволяет отлаживать слой в изоляции и подсовывать ему синтетические данные.
4. **Схема версионируется.** Версия схемы пишется в метаданные parquet. Шаг, получивший неизвестную версию, падает с понятной ошибкой, а не выдаёт мусор.
5. **Запись атомарная:** пишем во временный файл, потом переименовываем. Прерванный прогон не оставляет полуфайл, который выглядит целым.

### 4.1 Конфиг установки: `configs/venues/<venue_id>/`

| Файл | Содержимое | Откуда берётся |
|---|---|---|
| `venue.yaml` | размеры поля в метрах; пороги уверенности по классам; целевой fps обработки; модель и imgsz | вручную |
| `calib.json` | матрица камеры K, коэффициенты дисторсии, размер кадра. Может отсутствовать — тогда коррекция дисторсии пропускается | `cv2.calibrateCamera` по шахматной доске, либо по прямым линиям зала |
| `homography.json` | H (3×3) из неискажённых пикселей в метры; контрольные точки (пиксель ↔ метры), по которым H посчитана; ошибка репроекции | разметка точек мышкой, `cv2.findHomography` |
| `pitch_polygon` (внутри `venue.yaml`) | контур поля на кадре, в пикселях | разметка мышкой |
| `visible_polygon` (внутри `venue.yaml`) | часть поля, которую видит камера, в метрах | вычисляется из H и границ кадра |

**Система координат поля:** метры, начало — ближний к камере левый угол поля (как видно из камеры). `x` — вдоль длинной оси, от 0 до длины поля; `y` — поперёк, от ближней боковой линии до дальней. Размеры поля берутся из `venue.yaml`, в коде не зашиты.

### 4.2 Артефакты матча: `data/matches/<match_id>/`

**`meta.json`** — путь к видео, `venue_id`, fps исходника и fps обработки, версии модели и схемы, дата прогона.

**`detections.parquet`**

| поле | тип | смысл |
|---|---|---|
| `frame_id` | int32 | номер кадра в исходном видео |
| `ts` | float64 | секунды от начала записи |
| `cls` | category | `person` \| `ball` |
| `x1, y1, x2, y2` | float32 | бокс в пикселях исходного кадра |
| `conf` | float32 | уверенность |

**`tracks.parquet`** — все поля detections, плюс:

| поле | тип | смысл |
|---|---|---|
| `track_id` | int32 | идентификатор трека (это ещё **не** игрок, см. 4.3) |
| `foot_x, foot_y` | float32 | точка касания пола: центр нижней грани бокса, в неискажённых пикселях |
| `in_pitch` | bool | точка касания внутри `pitch_polygon` |
| `role` | category | `player` \| `goalkeeper` \| `referee` \| `unknown` |
| `team` | category, nullable | `A` \| `B` \| null (у судьи и неизвестных) |

Роль и команда присваиваются **треку целиком** голосованием по его кадрам и продублированы в каждую строку для удобства.

Роль и команда — два отдельных поля, а не одно `team_id` со значениями вроде `gk_a`. Так вратарь остаётся членом команды, и командные метрики его учитывают.

**`state.parquet`** — только строки с `in_pitch = true`:

| поле | тип | смысл |
|---|---|---|
| `frame_id, ts, track_id, role, team` | | как выше |
| `x_m, y_m` | float32 | позиция на поле, метры, после сглаживания |
| `vx, vy, speed` | float32 | м/с |
| `interpolated` | bool | точка восстановлена по соседним кадрам, а не наблюдалась |

**`metrics.json`** — по каждой команде и каждому треку:

- `observed_s` — сколько секунд объект был в кадре и на поле
- дистанция, дистанция в минуту наблюдения, максимальная скорость
- число спринтов (порог настраивается, по умолчанию 5.0 м/с — уточнить)
- тепловая карта: сетка с ячейкой 1 м
- по команде: компактность (площадь выпуклой оболочки игроков) во времени

**Каждая метрика несёт `observed_s`.** На установке вроде Костромы игроки регулярно уходят из кадра, и дистанция без указания покрытия молча занижается. Лучше честно показать «пробежал 1.2 км за 14 минут в кадре», чем «пробежал 1.2 км».

### 4.3 Трек — это не игрок

В футзале замены неограниченные и происходят на ходу. Игрок уходит на скамейку — трек обрывается; возвращается — начинается новый трек. Плюс трекер иногда путает игроков при пересечениях.

Поэтому в этом цикле:
- метрики считаются **по командам** и **по трекам**;
- привязка треков к конкретному игроку делается **вручную** в интерфейсе сервиса (фаза 6): пользователь отмечает, что треки 12, 31 и 58 — это игрок №7;
- автоматическое распознавание номеров — за рамками цикла.

Это ограничение продукта, о котором пользователь должен знать заранее. См. открытые вопросы.

### 4.4 Тестирование

- **L2 и L3** — модульные тесты на синтетических траекториях с заранее известным ответом: прямая с постоянной скоростью, окружность, остановка. Работают без видео и без GPU.
- **L1** — дымовой тест на 10-секундном клипе: пайплайн проходит, схемы артефактов валидны.
- **Качество** — отдельный прогон на размеченном наборе (фаза 2), не часть обычных тестов.

## 5. Фазы

Порядок углубления — CV → данные → сервис. Первым идёт тонкий сквозной срез, чтобы риски на стыках слоёв вскрылись сразу.

```
Ф0 установка ─────────────────┐ (нужен физический доступ, идёт параллельно)
Ф1 срез на Костроме ──▶ Ф2 валидация ──▶ Ф3 углубление CV ──▶ Ф5 мяч ──▶ Ф6 сервис
                                   └──▶ Ф4 метрики (параллельно с Ф3)
```

### Ф0. Установка целевой камеры (МССИ) — 1 неделя, параллельно

- `calib.json`: 20–30 кадров шахматной доски в зале, `cv2.calibrateCamera`. Запасной путь без доступа — калибровка по прямым линиям зала на самом видео.
- `venue.yaml`: реальные размеры футзальной разметки, измеренные рулеткой.
- `homography.json`: 6–8 контрольных точек на кадре после коррекции дисторсии.
- **Не техническая, но блокирующая задача:** получить полные записи матчей с этой камеры.

**Готово, когда:** ошибка репроекции на контрольных точках, не участвовавших в расчёте H, меньше 0.5 м.

### Ф1. Вертикальный срез на Костроме — 1–2 недели

Одна команда прогоняет 5-минутный фрагмент через все слои:

`detect (yolo11m, 1280, 10 fps) → track (ByteTrack) → фильтр pitch_polygon → команды по цвету (базово) → гомография → сглаживание → дистанция и тепловая карта`

- Фильтр по полигону поля входит сразу: без него две трети детекций — зрители (раздел 3.2).
- Гомография для Костромы **приблизительная**: углов поля в кадре нет, поэтому H строится по видимым ориентирам — дальней площади ворот, центральной линии — с допущением о стандартных размерах разметки. Допущение проверяется: ширина дальних ворот должна выйти ~3 м, скорости игроков — правдоподобными.
- Главный инструмент отладки, который появляется в этой фазе: **видео, где исходный кадр и схема поля сверху идут рядом синхронно.**

**Готово, когда:**
- весь фрагмент проходит одной командой, все артефакты по схеме раздела 4.2;
- собирается отладочное видео «кадр + вид сверху»;
- после сглаживания ни у одного трека скорость не превышает 10 м/с;
- ≥ 95% точек игроков в `state.parquet` лежат внутри границ поля в метрах. Это проверка согласованности гомографии и `pitch_polygon`: точка, прошедшая фильтр в пикселях, должна попадать на поле и после проекции.

### Ф2. Валидационный набор — 1 неделя

- 3 клипа по 30 секунд из Костромы. Если к этому моменту появятся записи МССИ — хотя бы один клип оттуда.
- Разметка в CVAT: боксы и идентичности игроков, роль, команда; контрольные точки поля. **Предразметку делает модель**, человек только исправляет.
- Метрики: полнота и точность детекции внутри поля; IDF1, MOTA и число переключений ID; ошибка проекции в метрах. **Всё отдельно по ближней и дальней половине поля.**

**Готово, когда:** одна команда пересчитывает все метрики качества, а исходные числа записаны в `docs/baseline.md`.

### Ф3. Углубление CV — 3–5 недель

В порядке ожидаемой отдачи:

1. Точный `pitch_polygon` вместо грубой линии.
2. Команды: кластеризация по цвету торса. Вратари — по позиции: трек, который держится у своих ворот. Судья — отдельно; на МССИ судью и вратаря цветом не разделить, только позицией.
3. Сшивка оборванных треков.
4. Дообучение детектора на своих кадрах — только если пункты 1–3 не дали нужного качества.

**Готово, когда** (ориентиры, уточняются после Ф2):
- переключений ID на валидации вдвое меньше, чем в baseline;
- команда определена верно для ≥ 95% трек-секунд;
- роль определена верно для ≥ 90% трек-секунд.

### Ф4. Состояние и метрики — 2–3 недели, параллельно Ф3

- Генератор синтетических траекторий.
- Сглаживание (фильтр Калмана), скорости, дистанции, спринты, тепловые карты, компактность, покрытие `observed_s`.
- Сначала всё пишется и тестируется на синтетике, потом прогоняется на реальных треках.

**Готово, когда:**
- на синтетике дистанция и скорости совпадают с точным ответом в пределах 2%;
- на реальном фрагменте дистанция в минуту наблюдения лежит в правдоподобном для футзала диапазоне.

### Ф5. Мяч — исследование, таймбокс 3 недели

- **Условие входа:** в валидационном наборе размечен мяч.
- Собственный детектор мяча (дообучение на своих кадрах), инференс по тайлам кадра, интерполяция траектории между пропусками.
- **Точка решения в конце таймбокса:** если полнота на ближней половине поля ≥ 60% — продолжаем к владению и передачам. Иначе фаза закрывается, продукт остаётся на физических метриках.

### Ф6. Сервис — 3–4 недели

- **Условие входа:** пайплайн стабильно отрабатывает минимум на двух полных матчах с целевой камеры.
- FastAPI, очередь задач, GPU-воркер, Postgres, объектное хранилище, дашборд.
- Интерфейс ручной привязки треков к игрокам (раздел 4.3).
- **Точка решения:** где крутить GPU-воркер. К этому моменту уже будет измерено реальное время обработки матча, и стоимость одного матча в деньгах можно посчитать, а не угадывать.

### Ф7. События — следующий цикл

Требует размеченного корпуса событий. Для футзала открытого корпуса нет, размечать придётся самим.

## 6. Риски

| Риск | Проявление | Что делаем |
|---|---|---|
| Нет полных записей с целевой камеры | Все фазы, кроме Ф1–Ф2, упираются в данные | Ф1–Ф4 идут на Костроме; получение записей — задача вне кода, запускается сейчас |
| Диск: ~12 ГБ свободно | Упирается уже на втором-третьем полном матче | Освободить 100+ ГБ или вынести `data/` на внешний SSD — до Ф2 |
| Поле не целиком в кадре | Заниженные дистанции, обрывы треков | `observed_s` в каждой метрике, `visible_polygon` в конфиге |
| Трек ≠ игрок | Пользователь ждёт метрики по игрокам | Ручная привязка в Ф6; предупредить пользователей заранее |
| Мяч не детектируется | Нет владения и передач | Таймбокс и точка решения в Ф5 |
| Приблизительная гомография на Костроме | Метры с систематической ошибкой | Проверки правдоподобия в Ф1; точная калибровка только на целевой камере |
| Права на видео Костромы | Нельзя обучать на нём коммерческую модель | Использовать для разработки и тестов; вопрос открыт до дообучения в Ф3 |

## 7. Стек и структура репозитория

**Стек:** Python 3.12, uv, ultralytics (YOLO11), supervision (ByteTrack, работа с полигонами), OpenCV, polars + pyarrow, pytest. Сервисная часть (Ф6) выбирается отдельно, к ней приступаем позже.

```
AI-football/
├── pyproject.toml
```

## 8. Открытые вопросы

1. **Полные записи с камеры МССИ** — кто может их дать и когда.
2. **Диск** — чистить внутренний или использовать внешний SSD.
3. **Размеры футзального поля в зале МССИ** — нужен замер рулеткой (Ф0).
4. **Метрики по игрокам** — готовы ли первые пользователи вручную привязывать треки к игрокам, или без автоматики продукт им не нужен. Ответ может сдвинуть распознавание номеров из «за рамками» в текущий цикл.
5. **Видео Костромы** — можно ли на нём дообучать модели, если продукт будет коммерческим.
6. **Порог спринта** — 5.0 м/с взят как стартовое значение, нужна опора на литературу по футзалу или мнение тренера.
