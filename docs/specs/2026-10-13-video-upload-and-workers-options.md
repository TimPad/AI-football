# Загрузка записей в S3 и варианты вычислений

Дата проверки документации: 13 октября 2026. Дополнение к [индивидуальной аналитике](2026-10-13-player-match-analytics-design.md). Это предложение устройства системы, а не уже развёрнутая инфраструктура.

## Рекомендуемое разделение

Постоянно доступны сайт/API, PostgreSQL и очередь заданий. Закрытое S3-совместимое хранилище содержит оригиналы, браузерные прокси и результаты. Отдельный обработчик запускает Python-конвейер, получает задания и возвращает артефакты. Он может работать на своём компьютере, облачной GPU-ВМ или в управляемой среде задач. Перенос обработчика не меняет пользовательский сценарий загрузки.

Отдельная физическая машина не обязательна для пилота. Отдельный процесс обработки необходим, чтобы длинные вычисления не занимали HTTP-запросы. Для регулярной автоматической эксплуатации рекомендуется отделить вычислительные ресурсы от сайта.

## Как файл из браузера попадёт в S3

1. Пользователь открывает матч → «Видео и аналитика» → «Загрузить запись», выбирает файл. Браузер передаёт API имя, размер и запрос создания загрузки. API проверяет доступ, создаёт `video_asset` и сессию с уникальным ключом объекта.
2. API инициирует multipart-загрузку в S3 и выдаёт временные подписанные ссылки для частей. Постоянный секретный ключ хранилища остаётся на сервере; бакет закрыт.
3. Браузер читает файл частями, например по 32–64 МиБ с несколькими параллельными запросами, и отправляет непосредственно в S3. Конкретный размер выбирается с учётом размера записи и лимитов поставщика. На сайте показываются прогресс, скорость и состояние повторов. Основной видеотрафик не проходит через сервер сайта.
4. При обрыве повторяются незагруженные части. Состояние сессии хранится в базе; после перезагрузки страницы пользователь при необходимости повторно выбирает тот же локальный файл. API сверяет уже сохранённые части с S3, проверяет соответствие файла и обновляет истёкшие ссылки. Закрытие браузера во время загрузки приостанавливает отправку.
5. По завершении API проверяет список частей и завершает multipart. Повтор запроса завершения безопасен. Файл получает статус «Проверяется», не «Готов к аналитике» только по сообщению браузера.
6. Фоновая проверка сверяет фактический размер, вычисляет SHA-256, проверяет видеопоток и декодирование, получает длительность/временные метки. Multipart ETag не считается SHA-256 всего файла. Готовится прокси для плеера; аналитика сохраняет доступ к оригинальному разрешению.
7. Пользователь выбирает интервалы матча/таймы и профиль камеры, нажимает «Обработать». Создаётся задание; сайт показывает ожидание, этапы и результат. После успешного завершения загрузки и регистрации задачи обработка не зависит от открытой вкладки.

S3 поддерживает [подписанные URL](https://yandex.cloud/ru/docs/storage/concepts/pre-signed-urls) и [multipart-загрузку](https://yandex.cloud/ru/docs/storage/s3/api-ref/multipart). Для браузера настраивается [CORS](https://yandex.cloud/ru/docs/storage/concepts/cors) на домен сайта, необходимые методы/заголовки и чтение ETag. Незавершённые старые загрузки отменяются по политике очистки; завершённый исходник не перезаписывается новой попыткой.

Альтернативные входы: импорт доступного файла Яндекс Диска через фонового загрузчика или передача большого пакета записей администратором через CLI с последующей регистрацией в API. Оба пути создают такой же проверенный `video_asset`. Обычная ссылка ВК предназначена для просмотра; автоматическое скачивание записи из ВК в этот сценарий не входит.

## Как обработчик получит и вернёт данные

Обработчик использует отдельный авторизованный HTTPS API: получить/арендовать задачу, запросить ограниченный доступ к её файлам, сообщить прогресс/heartbeat, зарегистрировать результаты. Прямой публичный доступ к PostgreSQL не нужен. API выдаёт только соответствующий задаче набор входов и выходов.

Задание содержит ID прогона, манифест источников и интервалов, снимок профиля камеры, версии моделей/кода и параметры. Обработчик скачивает нужный оригинал/фрагмент на рабочий SSD, выполняет конвейер и загружает неизменяемые результаты в S3. API проверяет их манифест/схемы и регистрирует результат; неидентифицированные фрагменты отправляются на экран проверки. Именно сервис записывает согласованную индивидуальную статистику в PostgreSQL.

Рабочий диск нужен для исходника, прокси/фрагментов, промежуточных артефактов и моделей. Его запас измеряется реальным конвейером; размер видеопамяти выбирается замером моделей при нужном разрешении. Скачивание и декодирование могут заметно влиять на общую длительность: GPU ускоряет прежде всего модели, а не все шаги.

Сначала один процесс выполняет полный конвейер. При росте нагрузки импорт/прокси и часть расчётов можно вынести на CPU, а детекцию/маски/OCR — на GPU. Это уменьшает время оплаченного GPU-простоя на вспомогательных шагах, но требует отдельных артефактов и замера реальной экономии.

Для прерываемых сред результаты этапов сохраняются в S3. Длинная детекция получает промежуточные блоки, чтобы не повторять весь матч; трекинг через границы блоков сохраняет состояние/правила согласования ID. Независимый трекинг отдельных кусков без согласования не считается единой траекторией. Результат попытки регистрируется только действующим владельцем аренды задания.

## Практические варианты размещения

| Вариант | Где используется | Ограничения и расходы |
|---|---|---|
| Имеющийся ноутбук/Mac/ПК | Пилот и небольшой объём; обработчик получает облачные задания | Должен быть включён и доступен сети. На Mac — нативный Python/MPS; скорость проверяется полным прогоном |
| Собственный отдельный ПК с NVIDIA | Регулярная загрузка, оператор рядом, доступное помещение | Покупка, электричество, обслуживание, резервирование и связь. Linux/CUDA-контейнер — практичный вариант запуска |
| CPU-обработчик на сервере сайта или CPU-ВМ | Проверка загрузки, прокси, метрики; экспериментально весь конвейер | Для полной нейросетевой обработки скорость пока не измерена. На одной машине ограничиваем ресурсы и очередь, чтобы сайт отвечал |
| Облачная GPU-ВМ по потребности | Автоматическая обработка периодических партий матчей | Запуск/инициализация и управление выключением; платятся используемые ресурсы, хранение и трафик |
| Постоянная GPU-ВМ либо арендованный выделенный GPU-сервер | Устойчивая высокая нагрузка и короткая очередь | Оплата вычислительного простоя либо фиксированной аренды; выгодность зависит от загрузки |
| Прерываемая/spot GPU-ВМ | Фоновая очередь, допускающая задержки | Возможны остановка и отсутствие ресурсов. Нужны промежуточные результаты, повторы и резервный обычный обработчик |
| Serverless GPU, например Runpod или Modal | Нерегулярная нагрузка, автоматический запуск контейнеров и масштабирование | Холодный запуск, лимиты времени/диска, платная загрузка моделей и данных, интеграция с внешним хранилищем |
| Colab Free | Ручные короткие эксперименты и проверка моделей в ноутбуке | Негарантированный GPU и динамические ограничения; бесплатные распределённые обработчики запрещены правилами |
| Colab Pro/Pro+/Pay As You Go | Ручная обработка матчей и исследования с большим доступом к ресурсам | Платный план также не гарантирует конкретный GPU и непрерывную работу; расходуются compute units |
| Управляемые batch/ML-задачи, например DataSphere Jobs | Автоматическая пакетная обработка с управлением окружением провайдером | Настройка контейнера/коннекторов/ресурсов, квоты и тарифы. Это отдельный вариант от интерактивного ноутбука |
| Гибрид: локальный обработчик плюс облачный резерв | Старт с существующего оборудования, дополнительные задачи при пиках | Один контракт заданий; правила маршрутизации и исключение двойного захвата |

Таблица описывает классы решений; выбрать любого провайдера внутри класса можно после замера производительности, доступности GPU, тарифа и условий работы с данными. Покупать оборудование до этого замера не требуется.

### Особенности Colab

Ручной сценарий: открыть ноутбук → выбрать ID подготовленного матча → получить временные ссылки → скачать запись на диск сессии → запустить тот же Python-код → сохранить завершённые этапы и результаты в S3 → передать манифест API. Исчезновение сессии не должно уничтожать уже сохранённые результаты. Прямой доступ ноутбука к рабочей базе и постоянный полный ключ бакета не нужен.

По [официальному FAQ Colab](https://research.google.com/colaboratory/faq.html), доступность GPU и ограничения динамические; бесплатные сессии ограничены, для paid-планов также возможны завершения при исчерпании compute units. Pro+ допускает до 24 часов непрерывного выполнения при достаточном балансе. Бесплатные managed runtimes ограничивают distributed workers. Поэтому для обычного Colab предлагается ручной экспериментальный запуск, а для автоматического сервиса — управляемая batch-задача или ВМ. Colab Enterprise/выделенные ресурсы — отдельный платный вариант.

Внешний обработчик не сможет обратиться к `127.0.0.1:8000` на компьютере организатора. Для постоянной схемы API разворачивается по HTTPS на доступном сервере. До развёртывания ручной эксперимент может возвращать файлы для локального импорта, без публикации PostgreSQL в интернет.

### Особенности облачных вариантов

У [Runpod Serverless](https://docs.runpod.io/serverless/endpoints/endpoint-configurations) таймаут выполнения по умолчанию 10 минут; его нужно настроить для полного конвейера. Артефакты сохраняются в нашем S3, не зависят от короткого срока хранения ответа платформы. У [Modal](https://modal.com/docs/guide/timeouts) по умолчанию 5 минут, настраиваемый предел до 24 часов. В обоих случаях выбирается асинхронная задача, браузер не ждёт результат в одном HTTP-запросе.

[DataSphere Jobs](https://yandex.cloud/ru/docs/datasphere/concepts/jobs/) поддерживает конфигурацию окружения, входов/выходов, Docker и коннекторы S3. Можно запускать такую задачу как обработчик одного матча, сохраняя основной журнал состояния в нашем сервисе.

[Прерываемая ВМ Yandex](https://yandex.cloud/ru/docs/compute/concepts/preemptible-vm) может остановиться раньше окончания вычислений, максимальный срок работы — 24 часа; документация рекомендует сохранять промежуточные результаты. Такой вариант появляется после проверки восстановления конвейера.

## Как сравнивать стоимость

Сравниваем полную стоимость успешно обработанного матча, включая повторы: вычисления, запуск и загрузку моделей/данных, CPU/память/диски, хранение оригиналов/артефактов, запросы S3, исходящий трафик и эксплуатацию. Тариф GPU может не включать остальные ресурсы. Для своего ПК учитываются покупка, срок использования, электричество и обслуживание. Для notebook-планов цена подписки не равна цене неограниченного числа матчей.

Пример расчёта без привязки к тарифу: 100 матчей при измеренных 30 минутах полного оплачиваемого времени на матч — 50 часов вычислительного ресурса, плюс дополнительные старты и повторы. Постоянная ВМ в 30-дневном месяце — 720 часов. Эти 30 минут — допущение примера, не наш замер. Итоговая цена ВМ определяется [тарифом Compute Cloud](https://yandex.cloud/ru/docs/compute/pricing) и выбранной конфигурацией; для другого поставщика берётся его актуальный тариф.

При 8 Мбит/с 45 минут записи занимают около 2.7 ГБ; 100 таких записей — примерно 270 ГБ оригиналов, отдельно от прокси и результатов. Это расчёт по условному битрейту. Для файла 3 ГБ при фактических 20 Мбит/с идеальная загрузка занимает около 20 минут, при 100 Мбит/с — около 4 минут; реальная сеть добавляет задержки. Возобновление важно независимо от выбранного GPU.

Обработчик рядом с S3 в том же облаке — первый кандидат для уменьшения передачи данных между площадками; отсутствие оплаты такого трафика проверяется по конкретному маршруту и тарифу, не предполагается автоматически. Локальный компьютер и Colab скачивают оригинал за пределы хранилища, что может увеличивать платный исходящий трафик.

## Рекомендация для проекта

Сначала делаем общую схему загрузки/очереди и запускаем пилот на существующем компьютере. В историческом прогоне M2 Pro детекция пяти минут заняла 268 секунд; экстраполяция детекции на 45 минут была около 40 минут. Источник: [результаты фазы 1](../phase1-results.md). Полный новый конвейер с масками и OCR ещё не измерен.

На репрезентативном полном матче замеряем общий срок, время каждого этапа, память/VRAM, диск и байты передачи. Затем повторяем на одной арендуемой GPU-конфигурации и считаем стоимость матча. Для автоматической эксплуатации первый кандидат — отдельная GPU-ВМ по потребности рядом с S3; managed batch — альтернатива при желании передать больше управления провайдеру. Colab оставляем для исследования.

Постоянная GPU-машина или покупка ПК становится обоснованной при измеренной регулярной загрузке. Serverless/spot выбираются после проверки возобновления и расчёта накладных расходов. Сайт и идентификаторы игроков остаются теми же при любом выборе.
