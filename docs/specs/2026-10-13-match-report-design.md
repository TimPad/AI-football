# Отчёт по матчу — дизайн

Дата: 2026-10-13. Основание: обсуждение в сессии; общая спецификация продукта —
`docs/specs/2026-09-23-futsal-analytics-design.md`.

## 1. Зачем и для кого

Отчёт по матчу для любительской или студенческой команды. Читают двое:

- **тренер или капитан** — картина по командам и сравнение игроков;
- **игроки** — свои цифры.

Отчёт — один HTML-файл. Открывается в любом браузере, в том числе на телефоне, пересылается в мессенджере,
работает без интернета. Вид — в духе Sofascore: тёмная шапка, вкладки, карточки, строки сравнения с полосками,
поле с зонами.

Цифры отчёта — физические и позиционные. Они не зависят от мяча, поэтому надёжны. Владение и передачи
по замерам на двух журналах приблизительны: находится около половины пасов, верных среди найденных около 60%.
Поэтому они показываются только по флагу `--with-ball` для сверки и не входят в отчёт по умолчанию.
Удары и другие события пайплайн не распознаёт, в отчёт они не входят.

## 2. Запуск

```
python -m aifootball.cli report --venue DIR --match DIR [--video V]
    [--halves 0:40-21:50,27:10-46:00] [--team-a "Альта-Тур 35+"] [--team-b "БлэкСкрап 35+"] [--with-ball]
```

Выход в папке матча:

- `report.html` — отчёт, всё внутри: SVG, картинки JPEG в base64, немного JS;
- `report.json` — те же цифры без оформления, для тестов и будущего сервиса.

Вход: `state.parquet`, `tracks.parquet`, конфиг площадки. Видео (`--video`) нужно только для миниатюр
и стоп-кадров. Без него отчёт строится без картинок. Названия команд по умолчанию — «Команда A (зелёные)»
и «Команда B (оранжевые)». Цвет берётся по центрам кластеров формы (`teams.team_color_centers`).

## 3. Устройство

| Модуль | Задача | Вход → выход |
|---|---|---|
| `analytics/periods.py` | Таймы | число людей на поле во времени, `--halves` → список интервалов `(начало, конец, название)` |
| `analytics/report_data.py` | Цифры отчёта | `state`, `tracks`, периоды, площадка → словарь `ReportData` (без HTML) |
| `report/svg.py` | Рисование | данные → SVG-строка: поле с разметкой, тепловая карта, трети, линейный график |
| `report/frames.py` | Картинки из видео | видео, номера кадров, боксы → JPEG base64: миниатюры игроков, стоп-кадры моментов |
| `report/render.py` + `report/template.html` | Сборка страницы | `ReportData` + SVG + картинки → `report.html` |

Поток: `state` + `tracks` (+ видео) → `periods` → `report_data` → `report.json` → `render` → `report.html`.

`report_data` не знает про HTML, `render` ничего не считает. Шаблон строится на `string.Template`
или f-строках, без новых зависимостей. JS только переключает вкладки и периоды и показывает подсказки
при наведении.

## 4. Таймы

- **Автомат:** по `tracks` считается число людей на поле (`in_pitch`) в окне 10 с. Перерыв — участок дольше
  2 минут, где на поле меньше 4 человек. Таймы — непрерывные участки игры до и после самого длинного перерыва.
  Пустые хвосты в начале и в конце записи отрезаются.
- **Флаг `--halves`** заменяет автомат. Формат: `м:сс-м:сс` через запятую. Проверяется, что интервалы
  не пересекаются и лежат внутри записи.
- Если перерыв не найден, отчёт строится одним периодом «Весь матч», и в шапке пишется, что таймы не определены.
- В отчёте три периода: «Весь матч» (объединение таймов), «1-й тайм», «2-й тайм».

## 5. Цифры

Всё считается внутри выбранного периода, только по `role == "player"`: вратари и судьи в командные цифры
не входят, вратари выводятся в таблице игроков отдельной строкой.

### 5.1 Обзор команд (строки сравнения)

| Строка | Определение |
|---|---|
| Дистанция, км | сумма дистанций треков команды (как в `analytics/metrics`) |
| Метров в минуту | дистанция / суммарное время наблюдения игроков × 60 — на одного игрока, не зависит от того, сколько игроков вне кадра |
| Бег быстрее 4 м/с, м | дистанция на шагах, где сглаженная скорость > `HSR_MS = 4.0` |
| Спринты | как в `metrics`: скорость ≥ 5.0 м/с не короче 1 с |
| Компактность, м² | средняя площадь выпуклой оболочки полевых игроков команды (как в `metrics`) |
| Ширина / глубина, м | средний размах игроков поперёк / вдоль поля по кадрам, где в кадре ≥ 3 игрока команды |

### 5.2 Где играла команда

- **Трети:** доля времени, когда центр команды (среднее положение её полевых игроков в кадре) находится
  в своей / средней / чужой трети. Свою половину команды в тайме определяет медианное положение её вратаря.
  Если вратаря в тайме не видно, трети для этой команды не показываются.
- **Тепловая карта:** секунды в клетке 1 × 1 м (`heatmap_s` из `metrics`), нарисованная на схеме поля.

### 5.3 По ходу матча

Метров в минуту по 5-минутным отрезкам внутри периода, отдельная линия на каждую команду.

### 5.4 Игроки

- В таблицу попадают треки, которые были в кадре ≥ `MIN_PLAYER_S = 60` с. Короче — только в командных суммах.
  Над таблицей пишется, что строки — это треки, а не люди. Пока нет ручной привязки, имя строки — «Игрок N»
  (N — порядковый по времени появления) с миниатюрой.
- Колонки: время в кадре, дистанция, м/мин, бег > 4 м/с, спринты, устойчивая макс. скорость.
- Карточка игрока: тепловая карта трека (та же сетка 1 × 1 м, что у команд в `metrics`) и те же цифры.
- **Устойчивая макс. скорость** — максимум скорости, сглаженной медианой за 0.5 с. Значения на пределе
  фильтра (`≥ 10 м/с`) отбрасываются. Если не остаётся ни одного значения, ставится прочерк.
- **Миниатюра** — вырезка бокса трека из кадра посередине его самого длинного непрерывного отрезка,
  120 px по высоте.

### 5.5 Моменты

Для каждого: время в записи, команда, «Игрок N», стоп-кадр 640 px в ширину с обведённым игроком.

- самый длинный спринт (по дистанции);
- самая высокая устойчивая скорость;
- самая «беговая» минута команды (скользящее окно 60 с по м/мин).

### 5.6 Мяч (только `--with-ball`)

Карточка «Владение и передачи (приблизительно)»: доля владения, передачи и точность из `compute_possession`
и `detect_passes`. Рядом текст с замеренной точностью и ссылкой на журналы сверки.

## 6. Честность цифр

- В шапке: «обработано X из Y минут» (сумма таймов из всей записи).
- У каждой строки игрока — время в кадре.
- Если у команды в периоде суммарное время наблюдения меньше 50% от «периода × 4 полевых игрока»,
  обзор помечается «мало данных».
- Пороги 4 и 5 м/с — стартовые. В общей спецификации порог спринта — открытый вопрос.

## 7. Размер и вид

- Миниатюры 120 px по высоте, стоп-кадры 640 px в ширину, JPEG с качеством 80. Ориентир — до 3 МБ на матч.
- Вёрстка под ширину телефона (≈ 360–420 px), на компьютере — та же колонка по центру.
- Цвета команд берутся из формы; если цвета неразличимы, используются зелёный и оранжевый.

## 8. Проверка

- Модульные тесты на синтетике: таймы по известной паузе и разбор `--halves`; трети, ширина и глубина,
  бег > 4 м/с на треках с заданной траекторией; устойчивая скорость отбрасывает выбросы и упор в фильтр;
  выбор треков для таблицы; SVG-функции выдают разбираемый XML.
- Тест сборки: `cli report` на маленьком синтетическом матче создаёт `report.html` и `report.json`;
  в HTML есть все вкладки и три периода; без `--video` нет `<img>`.
- На живых данных: отчёты по Ярославлю 1:00–4:00 и 10:00–13:00, просмотр в браузере, в том числе в узком окне.
- Полный матч: прогон всей записи Ярославля (≈ 55 мин, детекция ≈ 6 ч в фоне) для проверки автомата таймов.

## 9. За рамками

- Ручная привязка треков к игрокам (номер, имя) — следующий шаг после первых отзывов на отчёт.
- Удары и другие события. Первый шаг вне отчёта — клавиша «удар» в `tools.label_touches`,
  чтобы набрать эталон.
- Веб-сервис (фаза 6): `report.html` станет его страницей без переделки.
