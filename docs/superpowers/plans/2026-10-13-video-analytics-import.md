# План внедрения обработки видео и импорта аналитики

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Админ+ получает задание матча, обрабатывает локальное видео, импортирует результат, подтверждает игроков и получает статистику матча и историю каждого игрока без дублей.

**Architecture:** Первая поставка: ручной перенос `job.zip` → локальный CLI → `result.zip`, проверка на сайте, подтверждение и отдельная публикация. Вторая: установленный Processor получает задания и возвращает результаты по HTTPS. Третья: повышение качества CV и облачный обработчик, использующие тот же контракт.

**Tech Stack:** Существующие Python 3.12+, FastAPI, SQLAlchemy/Alembic, PostgreSQL, Pydantic, Polars/OpenCV, CV CLI, React/TypeScript, Vitest и Playwright. Новое облачное окружение первой поставке не требуется.

**Spec:** [Спецификация](../../specs/2026-10-13-external-processing-and-report-import.md).

**Схема:** [Интерактивная HTML-архитектура](../../architecture/2026-10-13-video-analytics.html).

**Решение зафиксировано:** 13 октября 2026. Этап 1 реализован 14 октября: [инструкция, приёмка и ограничения](../../2026-10-14-analysis-stage1.md). Реальная запись проверена на фрагменте с разрешёнными демо-UUID; реальные личности и спортивная точность полного матча ещё требуют проверки.

## Global Constraints

- Изменение аналитики требует `can_manage_analytics` («Админ+»), проверяемого API при каждом запросе. Существующим администраторам право автоматически не выдаётся.
- Оригинальное видео остаётся у оператора на этапе 1. На сайт возвращается структурированный результат.
- Размеры площадки и адрес вводятся вручную. CV использует метрическую геометрию и снимок камеры, GPS не требуется; Яндекс Карты — ссылка по адресу.
- Ключ человека — стабильный UUID `player_id`, не ФИО, номер формы или `track_id`.
- Снимок составов и геометрии задания неизменяем. Правки даты/судей не влияют на совместимость, правки значимого контекста требуют нового задания.
- В первом импорте назначаются целые фрагменты треков вручную. OCR, маски сегментации и редактура интервалов с пересчётом — последующие поставки.
- Неизвестные метрики — `null` с причиной. `observed_s` — «Время в анализируемом видео», не игровое время.
- Метрики всего матча и его таймов не суммируются повторно; новая версия не добавляет второй сыгранный матч.
- Подтверждение аналитики независимо от ручного протокола, публикация — отдельная команда. Счёт, голы и карточки остаются в протоколе.
- Архив проверяется до записи метрик/переключения версии. HTML из пакета не исполняется в кабинете.
- Исходные пакеты и старые подтверждённые назначения сохраняются; приватные файлы и таблицы входят в резервную копию.

## Review Focus

1. Потеря ответа после успешной загрузки/подтверждения: повтор возвращает прежний результат без дублей (задачи 3–5).
2. Камера/состав изменились между выдачей и импортом: пакет отклоняется; изменение только даты допускается (задачи 1, 3).
3. Два одновременных фрагмента назначены одному человеку: подтверждение блокируется, прежние показатели остаются доступными (задача 4).
4. Частичная запись, короткие и неизвестные треки: полнота показана явно; отсутствие данных не становится нулём или игровым временем (задачи 2, 5).
5. Новый прогон или восстановление из копии: история содержит один активный результат на матч, публичная версия выбирается отдельно (задачи 4, 6).

## Исходное состояние перед внедрением

| Уже есть в проекте | Реализуется по плану |
|---|---|
| Администратор, команды, UUID игроков, составы, матчи | Отдельное право Админ+ |
| Залы, размеры площадки, версии калибровки, CV ZIP | Задание со снимком контекста |
| CLI: детекция → трекинг → координаты → метрики → отчёт | Упаковщик, импорт, ручное назначение личности |
| Гостевое расписание/матчи, протокол, ВК-трансляции | CV-показатели матча и история игрока |

Прежний самостоятельный `report.json` не содержит гарантированных `match_id`, `player_id`, `job_id` и происхождения камеры. PDF/HTML сами по себе не создают индивидуальную статистику. Старые отчёты без выданного задания исключены из первой поставки; такой импорт потребует отдельного режима с ручным подтверждением происхождения.

## Контракт первой поставки

API и CLI первой поставки реализованы. Вторая и третья поставки ниже остаются планом.

```text
job.zip                          result.zip
  job.json                         manifest.json
  venue.yaml                       report.json
  homography.json                  track-index.json
  pitch_polygon.json               checks.json
  calib.json (при наличии)          thumbs/*.jpg
```

- `job.json`: `contract_version="1"`, UUID задания/матча/команд, `context_hash`, снимки составов со стабильными UUID, UUID камеры, геометрия, параметры обработки и единицы. Hash — SHA256 канонического JSON значимого контекста без даты/судей и общей ревизии матча.
- `manifest.json`: версия контракта, UUID прогона/задания/матча, hash контекста, `primary_period_key`, SHA256/длительность/разрешение видео, версии обработчика/моделей, интервалы анализа, список путей/размеров/SHA256. Список включает все файлы кроме самого манифеста. Hash оригинала — заявленный источник, а не доказательство его подлинности без доступа к видео.
- `track-index.json`: уникальные `track_id`, сторона A/B или неизвестная, роль, непересекающиеся интервалы `[start_s, end_s)` от начала оригинала, миниатюра или `null`, наличие метрик основного периода. Короткие треки сохраняются даже при отсутствии в таблице отчёта.
- `report.json`: адаптер текущего schema_version=1; один основной период, разрезы по таймам, метрики треков и совместимые метрические heatmaps.
- `checks.json`: полнота/ошибки/качество, покрытие записи, ограничения метрик. Критическая ошибка камеры или источника блокирует подтверждение.

Начальные настраиваемые лимиты: ZIP 100 MiB, распакованные данные 300 MiB, 2048 файлов, JSON 64 MiB, миниатюра 2 MiB. Проверять фактические байты, MIME и SHA256. Отклонять пути вне каталога, симлинки, вложенные архивы, исполняемые/неизвестные файлы, бесконечные/NaN/отрицательные значения, несовместимые карты и интервалы за пределами записи.

## Модель и интерфейсы

Новый `src/aifootball/service/analysis/` отвечает за сервисную аналитику; `src/aifootball/analytics/exchange.py` — за контракт; `src/aifootball/processor/job.py` — за локальный запуск и упаковку.

| Таблица | Назначение |
|---|---|
| `analysis_jobs` | Задание, матч, неизменяемый контекст/hash, автор, время |
| `analysis_runs` | Прогон, пакет/hash/приватный путь, качество, статус; уникальность `(job_id, content_hash)` для исходных импортов |
| `analysis_assignments` | `run_id + track_id`, UUID игрока либо исключение с причиной, ревизия проверки |
| `player_match_metrics` | Уникальность `(run_id, player_id)`, матч, показатели/качество/происхождение |
| `analysis_commands` | UUID запроса, digest payload, автор и сохранённый ответ для повторов |
| `matches` | Независимые `active_analysis_run_id` и `published_analysis_run_id` |

Подтверждённые назначения не редактируются на месте: новое ручное сопоставление создаёт новую версию проверки со ссылкой на тот же неизменяемый пакет. Дедупликация импорта возвращает исходный прогон; новая ручная версия создаётся отдельной командой и содержит `source_run_id`. Уникальность содержимого применяется к исходным импортам, а не блокирует ручные версии.

Реализованные endpoints с префиксом `/api/v1`:

```text
POST /matches/{mid}/analysis/jobs                     создать задание
GET  /matches/{mid}/analysis/jobs/{jid}/package        скачать job.zip
POST /matches/{mid}/analysis/imports                  принять result.zip
GET  /matches/{mid}/analysis                          внутренний отчёт и версии
POST /matches/{mid}/analysis/runs/{rid}/reviews        новая ручная версия
PUT  /matches/{mid}/analysis/runs/{rid}/assignments    назначения + expected_revision
POST /matches/{mid}/analysis/runs/{rid}/confirm        подтвердить и выбрать активную
POST /matches/{mid}/analysis/runs/{rid}/activate       выбрать прежнюю подтверждённую
POST /matches/{mid}/analysis/runs/{rid}/publish        отдельная публикация
GET  /players/{pid}/analysis                          история активных версий
GET  /public/matches/{mid}/analysis                   опубликованная версия
```

Все команды изменения получают `request_id`; успешный повтор с тем же payload возвращает прежний результат, с другим — 409. Команды проверки/версий также проверяют `expected_revision`.

- [x] Выполнить backend suite (`.venv/bin/python -m pytest --tb=short`), UI tests/build и полную текущую E2E suite на тестовой БД.

Независимые контрольные измерения и реальные личности полного матча остаются отдельной приёмкой.

**Критерий завершения этапа 1:** реальная запись прошла весь путь до статистики и истории игрока; повторы, права, несовместимые отчёты, overlap, версии и восстановление проверены. Работающий ZIP-экспорт или PDF-вложение отдельно не считаются завершением.

## Вторая поставка: подключённый Processor

Зависимость — принятый этап 1. После него составляется отдельный исполняемый план.

- [ ] Pairing и отзыв ограниченного токена оператора/обработчика; отзыв Админ+ блокирует последующие задачи/импорт. Пароль администратора и доступ к PostgreSQL программе не передаются.
- [ ] Исходящие HTTPS-запросы программы: получение назначенного задания, heartbeat/этапы, доставка прежнего `result.zip`; повтор без дублей.
- [ ] Локальный выбор видео и подтверждение запуска. Задание содержит данные, а не shell-код. Ручной импорт сохраняется как запасной путь.
- [ ] Кнопка «Обработать на моём компьютере» и настоящий прогресс при подключённой программе; отключение компьютера означает ожидание/потерю связи, не успех. Одно назначение не запускается конкурентно.
- [ ] Приёмка двух машин, отмены, отзыва, разрыва/возобновления связи. Для другой машины сайт должен иметь доступный сетевой адрес, не `127.0.0.1` оператора.

## Третья поставка: качество CV и облако

Это направления развития, каждое с отдельным планом перед реализацией:

- Сегментация игроков и OCR номера с confidence/командой как подсказка к UUID, не автоматическое окончательное решение.
- Хранение временных рядов, разделение/слияние треков и пересчёт интервалов; готовые агрегаты не делятся произвольно.
- S3 для оригиналов, задания/lease/повторы, VM/GPU worker; прежний контракт результата, проверки личности и страницы отчёта. Колаб допускается как внешняя среда исполнения, не обязательная инфраструктура.

Права/контекст — задача 1; обмен/качество/короткие треки — 2; ограничения ZIP/атомарность/повторы — 3; личности/версии/агрегаты — 4; отображение/история/публикация — 5; реальный матч/E2E/backup — 6. Локальный автоматический запуск, OCR и S3 отделены от первой поставки.
