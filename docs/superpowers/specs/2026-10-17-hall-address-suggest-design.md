# Адрес зала: подсказки из карт

17 октября 2026. Дополнение к [общему UX/UI-проекту](2026-10-17-tournament-onboarding-and-continuous-ux-design.md). Предложение; реализация не начата.

## Запрос и существующая основа

Пользователь просит подсказку адреса непосредственно при создании зала. Сейчас `HallPage.tsx` содержит обычный input и ссылку `YandexMapsLink`; backend уже хранит `address`, `latitude`, `longitude`. Текущий frontend при новом сохранении удаляет координаты из отправляемого draft — это нужно изменить, а не просто добавить список подсказок.

## Предлагаемый сценарий

1. Администратор вводит город, улицу или название спорткомплекса в «Адрес зала».
2. После 3 символов и 300 мс без изменений появляется до 7 вариантов. В строке видны объект и адрес, чтобы различать одноимённые залы в разных городах.
3. Выбор варианта заполняет адрес; отдельный запрос определяет координаты выбранного объекта. Выбор организации не перезаписывает введённое название зала.
4. Под полем появляется небольшая Яндекс Карта с выбранной точкой и переходом в карты. Карту можно свернуть; сама загрузка карты не блокирует форму.
5. Изменение текста после выбора сразу снимает привязку к прежним координатам. Для нового адреса требуется новый выбор либо явное сохранение вручную без точки.
6. Если подсказок нет или сервис недоступен, введённый адрес остаётся; можно продолжить вручную. Не подставлять случайный первый результат.

Тот же компонент работает в полной карточке зала и в быстром создании из формы матча. Стрелки выбирают вариант, Enter подтверждает выбранную подсказку, Escape закрывает список, Tab сохраняет обычный переход по полям. На телефоне список помещается в ширину формы.

Предложенные значения 3 символа, 300 мс и 7 вариантов — решения плана, а не требование пользователя. Геолокацию браузера не запрашиваем: пользователь вводит город сам; регион, если явно выбран в форме, только повышает релевантность.

## Источники и выбор поставщика

Выбор автора плана — Яндекс, поскольку он уже используется в продукте. Проверено по официальным источникам 17 октября:

- [Геосаджест: запрос](https://yandex.ru/maps-api/docs/suggest-api/request.html): поиск по вводу, адрес и идентификатор выбранного объекта.
- [Геосаджест: ответ](https://yandex.ru/maps-api/docs/suggest-api/response.html): объект содержит заголовок, подпись, адрес и при запросе `uri`.
- [Геокодер: запрос](https://yandex.ru/maps-api/docs/geocoder-api/request.html): `uri` выбранной подсказки используется для получения координат; порядок координат требует явного преобразования.
- [Условия использования](https://yandex.ru/dev/commercial/doc/ru/): бесплатный режим имеет ограничения на сохранение результатов. Для хранения адреса/координат из API и использования в закрытом кабинете до подключения нужно подобрать подходящие условия лицензии. Бесплатный тариф в плане не предполагается.

API-ключи и лицензия — зависимости подключения, а не уже настроенный сервис. В этой работе внешние запросы с ключами, покупки и активация аккаунта не выполняются. До подключения провайдера ручной адрес продолжает работать.

## Контракт и хранение

- Серверный адаптер `AddressProvider` отвечает за suggest и resolve; frontend не получает секретный серверный ключ. Ключ JS-карты, если выбран этот способ отображения, отдельный и ограничен разрешёнными доменами.
- `GET /halls/address-suggestions?q=...` — для администратора/Админ+, ответ `AddressSuggestion{id,title,subtitle,address}`. `id` — короткоживущий подписанный дескриптор выбранного URI; произвольный URL из клиента не запрашивается.
- `POST /halls/address-resolution` принимает `{suggestion_id}` и возвращает `{address,latitude,longitude,selection_token}`. `selection_token` связывает выбранный адрес и координаты на время заполнения формы; не сохраняет зал сам.
- В `HallCreate/HallUpdate` добавить необязательный `address_selection_token`; на сервере валидировать его соответствие адресной строке и координатам. Для ручного адреса токен и координаты отсутствуют. Старые координаты сохраняются при правке остальных полей зала.
- `address` остаётся отображаемой строкой. Сохраняются уже существующие latitude/longitude; для provenance добавить `address_source=manual|yandex` новой миграцией. Исторические значения не геокодируются массово.
- Снимок зала в матче сохраняет выбранную на момент назначения точку. Правка адреса зала не переписывает уже сохранённые снимки матчей.
- Лимиты запросов на пользователя, timeout 2 с, отмена запросов при новом вводе. Ответ предыдущего запроса не заменяет актуальную выдачу. Подсказки не кешируются постоянно; политика хранения следует выбранной лицензии.

## Приёмка

- Название спорткомплекса и обычный адрес дают выбираемые варианты; выбранный адрес и точка сохраняются при reload.
- Изменение адреса убирает старую точку; изменение размеров зала сохраняет прежнюю точку.
- Быстрый ответ на новый ввод не перезаписывается запоздалым ответом на старый.
- При timeout/429/неподключённом провайдере форму можно сохранить с ручным адресом.
- Даты/соперник в форме матча сохраняются после создания зала на месте.
- Тесты используют поддельный адаптер и синтетические ответы; live smoke проверяет подключённый провайдер отдельно, без зависимости обычного CI от его доступности.
