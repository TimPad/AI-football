# AI Football: UX/UI вокруг матча, первая поставка

Дата: 15 октября 2026. Статус: **проект спецификации для проверки пользователем**.
Основа согласована в разговоре: FotMob для чтения матча, Torneo/Tournify для организации, Veo для проверки аналитики. Пользователь выбрал приоритет компьютера для обоих сценариев. Это согласование подхода; данный письменный документ ещё требует проверки.

Связанные документы: [исследование референсов](../../2026-10-15-ux-ui-reference-audit.md), [методика рейтингов](2026-10-14-player-ratings-tournament-design.md), [локальная приёмка](../../player-ratings-local-acceptance.md).

## 1. Цель и результат

Зритель, организатор и Админ+ работают с одним матчем через согласованный визуальный язык. Первые ответы зрителю — кто играет, результат/статус, события, участники и доступная статистика. Организатор видит готовность матча и выполняет следующую задачу. Админ+ проверяет один фрагмент или эпизод в контексте материала, не прокручивая весь список треков до отчёта.

Успех первой поставки: связный путь от турнира к матчу, игроку и истории; одна глубина основной навигации; удобный desktop; карты и оценки внутри веб-сервиса; понятные состояния и независимая публикация. Расчёт метрик, идентичность людей и подтверждённые версии сохраняют действующую семантику.

## 2. Объём первой поставки

Включены:

- общие визуальные компоненты и адаптивные оболочки клиента/кабинета;
- публичные турнир, расписание, матч, карточка игрока и история опубликованных оценок выбранного турнира;
- обзор матча, официальный журнал и состав внутри страницы матча, существующие CV-метрики/карты и рейтинги;
- кабинет турнира, сценарии подготовки и ведения матча, участие/действия, очередь проверки CV/Qwen;
- общий экран публикации, отражающий отдельные версии протокола, CV, источников рейтинга и турнирного среза;
- минимальные read-only расширения контрактов для логотипов/ID команд, связи задания с импортами и чтения разрешённых версий статистики;
- устранение ошибочного статуса ожидающего задания после импорта результата;
- сохранение URL-контекста, черновиков, устойчивых повторов и доступности с клавиатуры.

Следующие поставки, исключённые из этого документа: полные публичные каталоги команд/людей с дополнительными личными данными, турнирная таблица команд и плей-офф, автоматический планировщик, общая командная статистика ударов/передач с проверенным покрытием, публичные карты отдельных действий, анимация траекторий, исходный видеоплеер со seek и синхронизацией, единый автономный HTML-экспорт, Connected Processor/S3/очередь/GPU-ВМ. xG/xA/PSxG/xT/VAEP не добавляются.

Первый релиз не содержит неработающих вкладок будущих функций. Старый CLI `report.html` остаётся отдельно обозначенным техническим экспортом; новый клиентский путь ведёт на веб-отчёт. Сам экспорт будет унифицирован отдельной задачей, а не ручной правкой сохранённого файла.

## 3. Пользователи и разрешения

| Роль | Основная работа | Ограничение |
|---|---|---|
| Зритель | Расписание, опубликованный протокол, карты/оценки и история | Только явные public DTO и опубликованные версии |
| Администратор | Турнир, команды, заявки, зал, календарь, ручной протокол и его публикация | Права соответствуют существующему API; новые права автоматически не выдаются |
| Админ+ | Участие/действия, закрытые эпизоды, проверка CV, расчёт и публикация рейтинга | Серверные `require_analytics_reader/admin` сохраняются |

Обычный администратор сохраняет существующее право чтения/работы с теми CV-данными, которые разрешены текущими endpoints. Новая оболочка не расширяет его доступ к закрытому пониманию матча, действиям и приватным рейтингам. Публичные представления доступны ему на тех же условиях, что гостю.

## 4. Навигация и URL

Существующие адреса сохраняются. Новые параметры — адресуемое состояние интерфейса, а не дополнительные уровни вкладок.

| Экран | Адрес/состояние |
|---|---|
| Клиентские турниры | `/` и `/watch` |
| Клиентский турнир | `/watch/tournaments/:id?tab=matches|ratings&view=list|grid&day=...&hall_id=...` |
| Клиентский матч | `/watch/matches/:id?tab=overview|events|players|stats|video` |
| Открытая карточка игрока матча | тот же URL + `player_id`, при наличии `snapshot_id` |
| Публичная история оценок | `/watch/players/:id?tournament_id=...&snapshot_id=...` |
| Кабинет турнира | существующий `/tournaments/:id?tab=matches|teams|players|halls|ratings|publication|rules` |
| Кабинет матча | `/matches/:id?tab=overview|lineup|protocol|review|participation|actions|report|publication|info|history` |
| Задача проверки | тот же адрес + `run_id`, `task=identity|episode`, `item_id`, `filter` |

Глобальный справочник команд/людей/залов остаётся по текущим маршрутам. Пункты игроков и залов внутри турнира показывают участников/площадки данного турнира и ведут к соответствующим редакторам; они не превращаются в новые независимые каталоги.

Начальный экран матча — обзор; прямой переход в протокол остаётся доступен параметром. Старые ссылки на матч продолжают работать. `tab=matches`, `teams`, `rules`, `ratings` турнира сохраняют текущий смысл.

Смена раздела сохраняет выбранный допустимый источник. Изменение фильтра использует replace, открытие/закрытие игрока — навигацию с корректным Back. Неизвестный параметр нормализуется к безопасному разделу; повреждённый UUID не инициирует загрузку приватного источника. Подмена `snapshot_id` не обходит проверку публикации на сервере.

## 5. Визуальная система и desktop

Направление: светлая нейтральная оболочка сервиса, тёмная площадка/медиа, один зелёный брендовый акцент. Фирменные цвета команд используются для их сравнения и символов; статус всегда имеет текст/иконку. Копирование бренда, рекламы, ставок и точных формул рейтинга референсов не входит в задачу.

Публичное содержимое: max-width 1440px, поля 24–32px; на широком экране основная колонка и боковой контекст около 300px. Основная аналитика располагает сравнение и поле рядом; таблицы используют доступную ширину. У страницы нет 480px-ограничения. Компактная панель игрока может иметь свою ширину 440–520px.

Кабинет: навигация 224px; рабочая область занимает остаток. На ширине от 1440px проверка имеет три области — очередь 240px, центральный материал не менее 420px, инспектор 300px. На 1024–1439px очередь открывается из отдельной кнопки/панели, материал и инспектор используют две колонки. Ниже 1024px области последовательно открываются; таблицы прокручиваются внутри своего блока. Состав страниц и разрешений остаётся одинаковым.

Одна шкала типографики и отступов: основной текст 14–16px, подписи 12–13px, заголовки 20/28px; числовые показатели используют tabular-nums. Информация плотная, но контролы не уменьшены до нечитаемого размера. Счёт — часть шапки матча, а не отдельный огромный hero.

Общие компоненты: `MatchHeader`, `SectionNavigation`, `SourceStatus`, `MetricValue`, `TeamComparison`, `PlayerTable`, `PlayerInspector`, `PitchMap/Legend`, `PublicationItem`, формы и панели ошибок/черновиков. В компоненты чтения передаются адаптированные public или private view models. Доступность кнопок определяется capability, а доступ к данным — сервером.

Подписи групп и компонентов оценки отображаются по-русски; внутренние ключи Finishing/Creation/Security и UUID раскрываются в деталях источника, а не заменяют понятные названия в основном отчёте.

После утверждения спецификации визуальная концепция должна покрыть публичный матч/статистику, календарь турнира и административную проверку с публикацией. Растровый концепт — референс дизайна; реальные таблицы, текст, SVG-карты и контролы остаются кодовыми. Он не используется вместо интерфейса.

## 6. Клиентский турнир и матч

### Турнир

На первом экране название/сезон, даты и переключение «Матчи / Рейтинги». Список матчей имеет статус, время, команды, счёт и отметку доступной VK-трансляции. Сетка — существующая структура «время × зал». День, зал и статус фильтруются без отдельного диалога подтверждения. После Back восстанавливаются фильтр и положение списка.

### Общая шапка матча

Названия и логотипы/инициалы команд, дата/время в timezone турнира, зал, статус, счёт. Счёт приходит только из опубликованного протокола. Известный факт и ещё не опубликованный результат не смешиваются; `null` показан как отсутствие опубликованного значения. Технический результат и серия пенальти помечаются отдельно.

Пять разделов: **Обзор · События · Игроки · Статистика · Видео**. На странице есть краткая информация о готовности данных; подробная техническая версия раскрывается по запросу.

| Раздел | Что показывает первая поставка |
|---|---|
| Обзор | Опубликованные ключевые события, состав/лидеры при наличии данных, основные CV-показатели и доступная трансляция |
| События | Журнал текущего опубликованного протокола, официальные авторы/состав; существующая ссылка на отдельный протокол сохраняется |
| Игроки | Список по двум сторонам из опубликованного состава, дополненный разрешёнными данными CV/рейтинга с явным источником |
| Статистика | Группы показателей игроков: удары/создание, передачи, защита, вратари, перемещения; командное сравнение только по существующим агрегатам CV |
| Видео | Настроенная VK-ссылка/iframe с запуском пользователем; исходное видео и закрытые кадры не предоставляются |

Входные данные для событий и состава загружаются по `public_protocol_id` текущего PublicMatch. Нет опубликованного протокола — краткое пустое состояние в соответствующем разделе. При отдельной публикации CV/рейтинга доступные игроки могут показываться с меткой своего источника, без утверждения, что весь официальный состав установлен.

Первые данные загружаются независимо. Ошибка карты не скрывает счёт, ошибка рейтинга не скрывает протокол. Неизвестная категория не создаёт убедительный фиктивный ноль в обзоре. Полный набор карточек будущего сервиса не заполняется placeholder-метриками.

## 7. Карточка игрока и публичная история

Открывается из состава, CV-таблицы и рейтинга; сохраняет страницу матча/турнира. На desktop — панель, на узком экране — доступный диалог. Видны имя из выбранного источника, номер этого матча, сторона, матчевые роли при наличии подтверждения, оценка и её причины, доступная карта и показатели.

Доли показывают успехи, известные попытки и процент; неопределённые исходы выводятся отдельно. При нуле возможностей процент не заменяется нулём. Физическая работа относится к наблюдаемому видео и имеет вес в оценке 0.

Источник роли — подтверждённое участие/строка рейтинга. Каталоговое амплуа, номер и среднее CV-положение не создают роль в матче. Схема стартовой расстановки 5×5 не рисуется без явных данных позиции; список игроков достаточен.

Ссылка «История турнира» использует существующий публичный rating history API. Турнир обязателен; название человека берётся из опубликованных строк, а не приватного каталога. История содержит только выбранный snapshot, его матчевые строки, роль, методику и даты. Нет опубликованных строк — объяснимое пустое состояние; полного профиля с возрастом/весом/фото первая поставка не обещает.

Все опубликованные roster/metric/rating записи относятся к стабильному UUID. Одно имя или номер не используются как join key. Подтверждённые names/roles не переписываются каталогом.

## 8. Источники и временные контексты

`ReportContext` хранит отдельно match ID, `protocol_public_id`, разрешённый CV run, rating snapshot, период и источник выбранного игрока. Единого фиктивного номера версии для разных публикаций нет.

- У официального журнала — версия опубликованного протокола.
- У карты/физики — опубликованный CV run и доступный период.
- У оценки — выбранный разрешённый snapshot и его сохранённые факты.
- Шапка расписания может отражать текущий статус матча; исторический рейтинг явно обозначен как историческое издание.

Карточка старой оценки не подставляет новую карту как будто она входила в расчёт. Если архивная карта не выдаётся public API, показаны сохранённые показатели snapshot и отсутствие совместимой карты. Текущую CV-карту можно открыть отдельно с названием текущего источника. Добавления endpoint архивных CV-карт в первую поставку нет.

Фильтр периода показывает только существующие предварительно рассчитанные интервалы отчёта. Смена периода не пересчитывает матчевую оценку и не переименовывает её в оценку тайма. `all` частичной записи подписывается «Обработанный фрагмент», полного подтверждённого источника — «Весь матч». Длительности видео, обработки и участия различны.

## 9. Карты и статистика

Карты первых экранов строятся из существующего `heatmap_s`, геометрии площадки и `orientation`. Подпись — время наблюдения/суммарное время игроков по ячейкам, а не касания мяча. Поле использует фактическое отношение длины/ширины; единицы и легенда обязательны. Метровые координаты не смешиваются с GPS.

Командные карты выбранного периода используют общую шкалу максимумов обоих массивов, с числовыми значениями в секундах. Индивидуальная карта имеет свою явно названную шкалу. Ячейки с нулём не выглядят как горячие области. При отсутствии наблюдений карта не строится. Неизвестное покрытие не обозначается полным; из существующей матрицы нельзя выдумать достоверность каждой ячейки.

В первой поставке нет визуального сглаживания, которое могло бы скрыть пропуски. В дальнейшем сглаживание допускается как отдельное представление с сохранением исходных значений и явной пометкой.

Доступные командные distance/observed_s/m_per_min/hsr/sprints/width/depth/compactness показываются из сохранённого отчёта по периоду. Если для публичного доступа поле сейчас не выдаётся, сначала проверяется whitelist и расширяется public DTO; приватный полный report JSON гостю не передаётся. Командный speed maximum выводится только если он определён текущим контрактом.

Группы ударов, передач и вводов вратаря в первой поставке показывают индивидуальные сохранённые факты рейтинга и их полноту. Командное число ударов не считается суммой произвольно выбранных игроков или CV-кандидатов. Публичная карта отдельного удара/передачи и общая командная агрегация этих категорий — следующие задачи.

## 10. Кабинет турнира и работа с матчем

Внутри турнира навигация группируется: **Работа** (матчи, рейтинги, публикация), **Участники и площадки** (команды, игроки, залы), **Настройки** (регламент и сведения). Общие справочники остаются доступными. Выбор турнира сохраняется при переходе в матч; история и заявка сезона отделены от текущего профиля команды.

Матч открывается обзором с состоянием и доступными задачами. Основные задачи находятся в одной навигации: подготовка/состав, протокол, проверка записи, участие, действия, отчёт, публикация. Сведения и история — дополнительные видимые пункты, а не вложенные вкладки аналитики. При ограниченной ширине навигация сворачивается в доступный список.

- Подготовка: регламент, обе заявки, зал, дата, VK-ссылка; камера нужна для CV, но не блокирует ручной протокол. Ошибка показывает причину и переход к исправлению.
- Команды: существующая форма логотипа/описания и таблица игроков, с выбором уже существующего человека. UUID, каталожный состав и заявка турнира различаются.
- Зал: вручную заданные адрес/размеры и текущая калибровка. Выбор зала в расписании обязателен по действующим правилам; Яндекс Карты служат навигации.
- Протокол: перед вводом режим «Вести матч», «Заполнить после матча», «Только итог». Последний использует текущие команды итога и явно сохраняет неизвестные события/полноту, а не подтверждает их отсутствие.
- Ведение: выбор игрока и события связан с текущим составом; ручные часы и очередь команд сохраняются. Повторные футзальные выходы ведутся участием; счёт/карточки определяются официальным протоколом.
- Участие/действия: существующие формы и версии доступны напрямую. Большие интервалы/источники помещаются в экспертные раскрытия, при этом явные проверки полноты не исчезают.

Навигация между задачами не стирает ввод. Подтверждённая версия доступна для чтения; изменение начинается действующей операцией новой проверки/редакции. Никакого редактирования старого snapshot на месте.

Очередь официального протокола имеет одного владельца на match/admin в редактирующем экране. Просмотр отчёта и предпросмотр публикации не создают второй экземпляр этой очереди и не перехватывают управление. Переход между задачами сохраняет pending команды; блокировка, конфликт и восстановление отображаются явно.

## 11. Рабочее место проверки Админ+

Выбран один run и один вид задачи: сопоставление личности либо проверка эпизода. Список фильтруется и листается локально по имеющимся данным; задание и источник всегда видны. Центральная область показывает имеющиеся thumbnails/evidence, интервалы и карту при наличии; инспектор — состав, подсказку номера, причины неопределённости и решение.

В списке личностей используются реальные состояния: назначен UUID, не назначен, исключён; конфликты номера отдельно берутся из Qwen suggestions. Сам факт подсказки не означает принятое назначение. У эпизодов — текущие решения accepted/corrected/rejected либо отсутствие проверки. Не создаётся универсальный искусственный процент готовности по всем этим объектам.

Фильтрация и пагинация меняют только видимость строк. При сохранении полного набора assignments сохраняются также скрытые строки; текущий PUT не превращается в случайную замену только видимого фрагмента. Черновик scoped по admin/run, revision/context проверяются сервером.

При переходе к другому run несохранённые правки сохраняются в собственном черновике; материал одного источника не назначается другому. Dirty состояние блокирует подтверждение/публикацию, пока действует существующий механизм проверки. Допустимы неизвестный номер/участник и отклонение с причиной.

### Статус внешней обработки

Связь run с job добавляется в краткий DTO. Импорт/новая review-версия одного job уже означает, что результат существует. Список не подписывает такой job «Ожидает обработки». Выданное задание без импортов имеет статус «Результат не загружен»; это не утверждение, что программа работает или остановилась.

У run используются «На проверке», «Подтверждён», отметки активной/опубликованной версии. Из прошлого импортированного run не следует готовность нового job. Облачных процентов, очереди и кнопки удалённого запуска в первой поставке нет.

## 12. Единый экран публикации

Экран доступен из матча и из списка готовности турнира; выбранный матч сохраняется при возврате. Он агрегирует чтение текущих источников и вызывает существующие независимые команды.

| Блок | Видно | Действие |
|---|---|---|
| Протокол | Последняя подтверждённая и опубликованная версии, неполные категории | Подтвердить/опубликовать конкретную версию по текущим правилам |
| CV | Выбранный подтверждённый и опубликованный run, проверки качества | Опубликовать конкретный допустимый run |
| Участие/действия | Подтверждённые версии и текущие разрешённые версии | Разрешить выбранные источники и policy |
| Рейтинг турнира | Private/public snapshot, stale, текущий опубликованный срез | Рассчитать public snapshot, затем явно опубликовать его |

Публикация рейтинга остаётся операцией турнира. Из экрана матча переход передаёт турнир и возвращает на тот же матч; подпись не создаёт впечатления отдельного независимого рейтинг-среза этого матча.

Предпросмотр гостя использует public DTO, показывая то, что уже опубликовано. Предпросмотр выбранной ещё приватной версии доступен только Админ+ как отдельное представление с явной подписью «В кабинете». Он не выдаётся гостевой ссылкой и не называется текущим опубликованным отчётом.

Неполный CV не блокирует публикацию допустимого ручного протокола. Изменившиеся источники требуют пересчёта нового public snapshot; старый публичный остаётся до новой публикации. Кнопки выполняют конкретные операции, без скрытого «опубликовать всё» и без обещания общей транзакции. Ошибка одной операции не подписывает другие выполненными.

Причины блокировки видны рядом с кнопкой и имеют переход к соответствующей задаче. Frontend не придумывает более строгие условия полноты/оценки, чем сервер. После сохранения версии/расчёта данные готовности обновляются.

## 13. API и данные первой поставки

Изменения схемы хранения заранее не требуются: используются текущие ID, публикационные указатели и версии. Если реализация обнаружит необходимость нового сохраняемого поля, добавляется новая Alembic-миграция; существующие 0010–0013 не редактируются.

Обязательные минимальные расширения:

1. `PublicMatch`: ID обеих команд и nullable ID логотипов. События/состав по-прежнему загружаются из опубликованного протокола. Существующие поля и семантика счёта сохраняются.
2. `GET /public/catalog/team-logos/:image_id`: выдаёт только нормализованный логотип, связанный с командой видимого турнира. Непривязанный файл, photo_id игрока и архивные/невидимые связи не становятся общим каталогом изображений. Текущий защищённый `/catalog/images/:id` сохраняет guard. Текущий логотип — брендинг, а не исторический факт старой версии; имена состава/рейтинга берутся из соответствующих snapshots.
3. `AnalysisRunSummary`: добавить `job_id`; краткая сводка не включает raw understanding или секретные параметры. Статус job вычисляется по импортированным runs, без новой фиктивной таблицы фоновой обработки.
4. `GET /matches/:id/performance-publication`: право `require_analytics_reader`, возвращает существующий `PerformancePublicationView`. `revision` — текущая ревизия `TournamentRatingState`, используемая PUT как expected_revision, либо 0 при отсутствии state; это не локальная ревизия `RatingMatchPublication`. При отсутствии publication выбранные версии nullable. `policy_approved` сохраняет смысл текущего ответа PUT: наличие разрешённой policy; совместимость policy конкретного публикуемого snapshot дополнительно проверяет сервер. GET ничего не создаёт/не подтверждает; PUT сохраняет существующие проверки и request idempotency.

Для публикационного экрана первый релиз читает существующие match/protocol versions, analysis overview, participation/actions overview, новый publication GET и tournament analytics. Это один согласованный frontend view model с отдельными источниками; нового batch publish endpoint нет. Недоступный по роли запрос не выполняется только потому, что используется общий компонент.

Существующие public APIs протокола, CV, матчевых рейтингов и рейтинга/истории турнира переиспользуются. Публичная история показывает уже опубликованные поля; приватный PlayerHistory не переиспользуется вместе с его приватными HTTP-запросами.

Новые глобальные public team/player profile endpoints и публичная выдача фотографий исключены. Для элементов без публичной картинки используются инициалы/номер, а не приватный URL, который работает только у вошедшего администратора.

Шапка и выбранный раздел загружаются первыми; независимые запросы выполняются параллельно. Подробный CV run/закрытое understanding загружаются только для выбранного отчёта/задачи. Список готовности турнира использует существующие сводки; подробные versions одного матча запрашиваются при его открытии, без одинакового полного набора запросов для всех строк. Ответ предыдущего match/run не подставляется после смены контекста.

## 14. Состояния, сохранение и доступность

| Ситуация | Поведение |
|---|---|
| scheduled / live / ended / postponed / cancelled | Явный статус; текущие серверные правила доступности операций |
| Нет опубликованного результата | Счёт отсутствует; не подменяется приватным текущим итогом |
| Есть протокол, нет CV | События/состав доступны; аналитика показывает краткое отсутствие источника |
| Есть частичный CV | Длительность/источник видны, показатели ограничены наблюдаемыми интервалами |
| Нет рейтинга / недостаточно reference | Состав и физика доступны, причина отсутствия оценки краткая |
| Historical / stale | Выбранное издание сохраняется; переход к текущему явный; stale не переписывает старое |
| Loading / endpoint error | Состояние конкретного блока; работающие блоки сохраняются |
| Lost response / 409 | Черновик и request_id сохраняются; повтор либо сверка без двойной записи |
| Повреждённый локальный ввод | Возможность скачать исходный ввод до очистки, по текущему механизму |

Открытие карточки переносит фокус внутрь, Escape закрывает её, фокус возвращается в исходную строку. Back не теряет турнир/snapshot. Командные формы имеют подписи и клавиатурные действия. Цвет не является единственным сообщением о статусе. `prefers-reduced-motion` учитывается; декоративная анимация не заменяет реальное состояние обработки.

## 15. Граница общей системы отчёта

Компоненты представления отделены от загрузки/публикации/редактирования. MatchReport принимает уже разрешённые данные и контекст версии; публичный loader не получает приватный полный run. Кабинет может использовать те же таблицы/поле с дополнительными источниками и возможностями.

Старый Python-renderer не используется как iframe внутри нового сервиса. Это сохранило бы две навигации и две дизайн-системы. Единый offline export позднее должен использовать тот же согласованный набор компонентов/данных и выбранные версии, с отдельной политикой публичного/закрытого материала.

## 16. Критерии приёмки

1. **Desktop:** публичный отчёт 1280/1440px и кабинет 1440/1600px используют широкую область; нет корневого горизонтального overflow. Дополнительно 390px и 1024px, таблицы прокручиваются локально.
2. **Путь зрителя:** список/сетка → матч → события/игрок → карточка → история; Back и refresh восстанавливают URL и разрешённый snapshot. Гость не попадает на административный login ради истории опубликованных оценок.
3. **Путь организатора:** команда с существующим UUID → заявка/зал → матч → протокол → подтверждение/публикация. Незавершённая аналитика не блокирует допустимый ручной результат.
4. **Админ+:** один фрагмент из очереди → материал → решение → сохранение → следующий; скрытые assignments сохраняются. Новая версия не меняет старую.
5. **Публикация:** текущие разрешённые версии читаются без мутации; после пересчёта/publish статусы обновляются, guest и cabinet читают свои источники. Private/unpublished snapshot не открывается подменой URL.
6. **Карты:** общий масштаб сравнения, числовая легенда, геометрия зала и корректная подпись частичного периода. Отсутствие/ноль наблюдений не создаёт горячую карту.
7. **Границы:** нет private JPEG/notes/фото в public DTO или публичных запросах; для team-logo route — отдельная проверка связанного/несвязанного изображения.
8. **Регрессии:** сохранены проверки official/manual vs CV, UUID, clock axes, идемпотентности, lost response, 409 и historical edition. Методика/числа рейтингов не изменились.
9. **Визуальная приёмка:** утверждённая концепция сопоставлена с браузерными скриншотами по иерархии, ширине, типографике, картам, таблицам и ключевым состояниям. Build отдельно не доказывает визуальное соответствие.
10. **Среда:** ordinary tests используют синтетические данные и выделенные БД; демонстрационная запись используется только для ручного просмотра. Рабочая база организатора не очищается.

## 17. Решения и цена

- Первый релиз пересобирает существующие сценарии, а новые аналитические алгоритмы/турнирные структуры выделены отдельно — иначе редизайн превратится в новую вычислительную платформу; цена: не все функции референсов доступны сразу.
- Public player route ограничен историей опубликованных оценок и контекстной карточкой — это использует уже проверенный API; цена: нет полного публичного биографического профиля.
- Логотипы получают отдельную ограниченную выдачу — текущий image endpoint закрыт; цена: небольшой новый read-only контракт и проверки связей.
- Статус job строится по настоящим импортам — удалённой телеметрии нет; цена: оператор сам контролирует внешнюю программу.
- Историческая оценка не получает текущую CV-карту автоматически — версии независимы; цена: некоторые исторические карточки остаются без карты.
- Общий экран публикации сохраняет отдельные команды — backend не имеет общей атомарной операции; цена: несколько явных действий вместо одной кнопки.
- CLI-export не переписывается в первой поставке — клиентский путь унифицируется через веб-отчёт; цена: технический автономный HTML пока сохраняет старое оформление.
