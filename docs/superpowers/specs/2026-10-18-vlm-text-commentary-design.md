# Текстовая трансляция VLM во время обработки записи

Дата: 18 октября 2026, Europe/Moscow. Статус: предложение для согласования; код не изменён.

## Решения пользователя и цель первой поставки

Пользователь хочет улучшить понимание остановок/возобновлений, начала/конца, голов и номеров, затем получить хайлайты с использованием звука комментаторов и автоматические комментарии. Для озвучки выбран порядок: готовая запись, позже прямой эфир. Уточнён первый результат: **автоматическая текстовая трансляция VLM уже в ходе обработки матча**. Во время обработки её видит организатор; зрители — только после публикации результата.

Дополнительное требование пользователя: усиление VLM должно сохранять экономичность. Модель не должна заново разбирать тот же материал для каждой функции; нужен один совместный разбор с переиспользованием результатов. «Разом» означает совместный результат одного запроса на фрагмент, а не обязательную отправку всего матча одним огромным запросом.

Первая поставка: обработчик выдаёт реплики по мере готовности фрагментов, кабинет показывает их без ожидания итогового ZIP, после импорта и технического подтверждения выбранная версия ленты публикуется вместе с видеоанализом. Проверка каждой реплики человеком не является обязательной. Ручной протокол, назначения капитанов, метрики и публикация сохраняют свою независимость.

Пример формата (вымышленные реплики; время видеозаписи): `12:31 — Команда в светлой форме развивает атаку справа`; `12:36 — Удар по воротам, вратарь отбивает мяч`. Пустой/неразличимый фрагмент может дать ноль реплик.

## Что уже есть и что предстоит добавить

- `processor/job.py` выполняет CV, затем опциональный `run_understanding`, затем собирает ZIP. Первый текст в этой поставке появляется на этапе VLM **после подготовки CV**, а не сразу после запуска процесса. В UI подготовка обозначается отдельно. Ускорение первого текста через параллельную/полностью пофрагментную обработку — следующий этап.
- `processor/understand.py` сохраняет ответы, бюджет и восстановление локально; `understanding/reconcile.py` согласует окна, но итог пока возвращается после всего прохода. Идентификаторы согласованных событий зависят от набора окон и не годятся как постоянные ID строк потока.
- Сервис получает результат через импорт ZIP; канала промежуточных реплик пока нет. Его ограниченный вариант входит в проектируемую поставку. Это не обещание готового Connected Processor: автоматический запуск GPU, S3, lease очереди заданий и Colab сюда не входят.
- Обмен уже поддерживает версии **1/2/3**, причём v3 занят `events.json` по мячу. Для пакета с лентой нужна следующая версия **4**, с сохранением поддержки 1–3.
- По [замерам 16 октября](../../2026-10-16-ux-analytics-audit.md) общий план и ауты распознаются ненадёжно. Новая лента — проверяемая гипотеза о полезности описания, а не доказательство улучшившейся спортивной точности.

## Продуктовый сценарий

1. Админ+ создаёт обычное задание и включает текстовую трансляцию для этой обработки. До старта видны выбранная модель/режим и жёсткий бюджет запросов/токенов, включая повторы. Новых платных вызовов без явного запуска нет.
2. Для готового `job_id` создаётся частный поток. Оператор запускает существующий локальный обработчик с отдельным разрешением доставки. Пока CV не готов, кабинет показывает «Подготовка видеоанализа»; затем «Формируется текстовая трансляция».
3. После каждого валидного окна реплики автоматически попадают в кабинет, сортируются по времени исходника, уточнения обновляют прежнюю строку. Видны: «Текст сформирован до …», полоса реально обработанного покрытия и пропуски. Это не часы матча и не ETA.
4. При сбое сети обработка и локальный журнал сохраняются, доставка догоняет после восстановления. При исчерпании бюджета статус «Остановлено по лимиту» и известное покрытие; отсутствие новых реплик не маскируется бесконечным индикатором.
5. Итоговый пакет импортируется существующим путём. Лента связывается с конкретным run только после проверки исходника, контекста и содержимого. Организатор может читать её автоматически, необязательно править каждую строку; допустимы скрытие/редактирование отдельной реплики до технического подтверждения.
6. Техническое подтверждение замораживает снимок ленты. Существующее действие «Опубликовать аналитику» публикует этот снимок. Новая обработка/черновик не меняет старую опубликованную ленту. Для правки подтверждённого результата создаётся новая версия проверки, публикация выполняется отдельно.

Авторский выбор: «организатор» в первом варианте означает существующее право **Админ+**, поскольку лента относится к закрытой видеоаналитике. Капитан получает прежний доступ к своим заданиям, но не ко всей необработанной ленте. Обычный администратор не получает новое право на приватную аналитику. После публикации доступны публичные тексты.

## Наблюдения и генерация реплик

- Qwen остаётся существующим настраиваемым поставщиком; новую модель без замера не выбираем. Реплика формируется из проверенного структурированного ответа того же окна: отдельного вызова «переписать красиво» на каждую строку нет. Нужен небольшой версионированный контракт реплик/ссылок, отдельно от текущего строгого понимания; при отсутствии достаточных оснований — пустой результат.
- Базовый проход использует последовательные фрагменты с единым ответом для всех потребителей. Текущий планировщик 12-секундных окон с шагом 6 секунд пересматривается по правилам экономии ниже; его постоянное перекрытие не переносится как default. Изменение доставки не считается доказательством улучшения точности нового планировщика.
- Реплика: короткое описание видимого эпизода, по умолчанию до 220 символов, максимум два предложения. Повтор «идёт борьба» в каждом окне не нужен. Нельзя сочинять намерения, оценки силы команд, итоговый счёт, имя или решение судьи по одной реакции.
- Реплика содержит интервал, точку привязки, ссылки на исходные события/состояния и evidence. Модель возвращает локальное время окна; код один раз переводит его в шкалу исходника. Текст без проверяемого основания отбрасывается. Самооценка уверенности модели не является вероятностью истинности.
- До подтверждения A/B используем нейтральные описания формы/действий. Номер допустим только с читаемым кадром. Подтверждённый UUID и имя берутся из назначения и снимка состава; модель не выбирает человека по фамилии. Отсутствие номера не блокирует общую текстовую ленту.
- Определение официального гола/счёта требует связи с опубликованным или выбранным подтверждённым протоколом; его версию сохраняем. В первом варианте свободному тексту не поручается счёт. Неподтверждённый эпизод формулируется как кандидат/наблюдение; ручной протокол не изменяется.
- Полнота просмотра и точность события — разные вещи. Мяч вне кадра не означает остановку; непокрытый диапазон остаётся неизвестным. В первой поставке показываем время видео, без выдуманного чистого времени/минуты тайма. Будущий модуль часов будет опираться на регламент и отдельную проверенную временную привязку.

## Единый разбор и экономия токенов

Это уточнение заменяет прежнюю идею нескольких независимых полных VLM-проходов для описания, событий, номеров и проверки. Специализация допускается внутри одного контракта или в адресном уточнении недостающего наблюдения. Нельзя объявлять рост числа запросов улучшением качества без замера.

1. **Один базовый запрос на фрагмент.** Готовим краткий контекст CV и доступной геометрии, проверенные стороны команд, релевантные измерения, различимые кропы и ограниченную память соседних эпизодов. Контекст передаём только там, где он реально рассчитан или подтверждён; OCR и другие отсутствующие модули не подменяем выдуманными данными. Модель одним структурированным ответом возвращает наблюдения/номера, события, состояния, фазы и короткие реплики. Признаки интересного момента и временные границы также входят в этот ответ как кандидаты для будущего монтажа. Номер допускается неизвестным; отдельный identity-проход по всем трекам по умолчанию не запускается. Полный модуль хайлайтов, проверенные часы и озвучка остаются следующими поставками.
2. **Общие сохранённые наблюдения.** Лента, кандидаты хайлайтов и переходы состояний используют один журнал эпизодов с evidence и ограничениями. Дедупликация, привязка подтверждённых UUID/имён, расчёт часов при наличии проверенных правил, выбор/нарезка клипов, публикация и повторная доставка выполняются кодом поверх сохранённого результата. Изменение подписи команды, назначения капитаном или публикации само по себе не запускает визуальный анализ заново. Озвучка использует готовый текст; возможная генерация речи учитывается отдельно и не требует повторно отправлять видео в VLM.
3. **Убираем избыточный медиавход.** Текущий native-клиент отправляет клип и JPEG общего плана из того же времени; это надо пересмотреть. Авторский default для нового режима — видеоклип как основной визуальный вход, а дополнительные изображения только для деталей, неразличимых в нём, например читаемого номера. Альтернатива для контрольного сравнения — отобранная последовательность кадров без повторной передачи клипа. Полный второй набор общего плана по умолчанию не отправляется. Evidence сохраняется локально; контракт native-режима должен принимать ссылки на переданный clip и локальные интервалы. Код извлекает соответствующие JPEG для просмотра и проверяет границы/хеши, но не утверждает, что модель увидела отдельный JPEG, которого не было в запросе. Кропы сохраняют собственные переданные evidence IDs. Изменение контракта версионируется; старые ответы не переинтерпретируются.
4. **Покрытие без постоянного двойного просмотра.** Авторский default базового планировщика — соседние неперекрывающиеся интервалы и краткая память последних наблюдений с их исходными ссылками. У эпизода может сохраняться открытый статус до появления развязки в следующем фрагменте; это обновление той же сущности. Если граница скрывает важный переход, допускается ограниченный адресный просмотр границы в квоте уточнений. Ни полное устранение любого повторного кадра, ни сохранение точности при отказе от перекрытия заранее не обещаются: измеряем ошибки на границах и фактические токены.
5. **Ограниченный контекст.** Не накапливаем в каждом запросе весь транскрипт, прошлые видео и все треки матча. Код собирает небольшую память из последних относящихся к фрагменту эпизодов и открытых вопросов; лимит и версия сборщика фиксируются до запуска. Неподтверждённое остаётся неопределённым, а не превращается в установленный факт из-за повторения в памяти. Кропы выбираются по качеству и уже закрытой потребности, с лимитом на запрос; по возможности идут в тот же базовый запрос. Стабильно подтверждённый номер не перечитывается для каждого кадра. При разрыве/слиянии трека или противоречии прежняя связь не переносится автоматически; UUID остаётся независимым от track ID и номера.
6. **Кеш именно оплаченного входа.** Ключ включает хеши реально отправленных медиа, их роли/время, точный эффективный контекст и промпт, модель/endpoint/режим/настройки и версии контрактов. Доступ к кешу ограничен разрешённым рабочим пространством. Внешние job/attempt ID и весь изменившийся файл треков не должны сами по себе уничтожать совместимый кеш неизменившегося фрагмента; зависящий от них фактически отправленный контекст входит в ключ. Изменение существенного входа создаёт новый ключ и учитывается как новый анализ, а не как бесплатный replay. Сохраняем сырой ответ и usage до проверки/проекций. При resume, новой упаковке, доставке, публикации и допустимом пересчёте производных сначала используем сохранённый ответ; локально исправимую сериализацию/ссылки повторным платным запросом не лечим.
7. **Адресные уточнения и один исполнитель.** До дополнительного вызова записываются конкретный незакрытый вопрос, новый полезный материал и причина, почему базовый ответ недостаточен: например, новый качественный кроп номера или фрагмент развязки. Общий низкий confidence не является самостоятельным триггером. Совпавшие запросы разных потребителей объединяются, а атомарная запись pending/response в журнале не позволяет двум процессам одновременно отправить один ключ. При неизвестном исходе после таймаута или падения процесса запрос отмечается `outcome_unknown` и автоматически заново не отправляется. Без подтверждённой идемпотентности поставщика нельзя обещать exactly-once оплату: явный повтор такого запроса требует решения оператора в пределах бюджета, риск повторного списания показывается. Если поддержка провайдером поиска/повтора по ключу будет проверена, можно использовать её отдельно. Полученный невалидный, но полностью сохранённый ответ сначала разбирается локально; платное исправление допускается только как учтённое адресное уточнение, без незаметного повторного полного просмотра.
8. **Единый бюджет всех потребителей.** Базовый проход, номера, уточнения, исправления ответа и известные повторы расходуют общий лимит. Для базового покрытия резервируется бюджет; уточнения имеют отдельный подлимит и не отнимают уже зарезервированное покрытие. Перед запуском показываем оценку и границы, затем фактические usage и отдельно неизвестные расходы/консервативные резервы. Смена модели или увеличение бюджета требует явного действия, автоматической цепочки всё более дорогих моделей нет. Потерянный ответ не считается бесплатным. Цена оценивается по проверенному тарифу на дату пилота; гарантировать нулевую оплату неизвестного исхода или точную экономию заранее нельзя.

Авторский выбор порядка работы: сохраняем первый базовый разбор после готовности CV, чтобы сразу передать контекст и кропы. Для ускорения первого текста позже допускается конвейер, где CV готовит следующий фрагмент, пока VLM разбирает предыдущий. Независимый ранний VLM-проход и обязательный второй проход с поздним CV-контекстом в стандартный режим не входят. Это уточняет ранее предложенную в разговоре параллельную ветку с учётом требования экономии.

Проверка экономии: на одинаковых размеченных фрагментах сравниваем текущий режим и единый разбор по токенам/минуту, числу и причинам дополнительных запросов, полезному покрытию, точности, ошибкам на границах и времени первой строки. Успех не измеряется одним снижением числа HTTP-вызовов: длинный запрос тоже может быть дорогим. Повторный запуск с теми же эффективными входами, обновление интерфейса, подтверждение состава и публикация должны давать ноль новых VLM-вызовов. Отдельные проверки: конкурентный запуск одного ключа, crash после отправки, потерянный ответ, локальная перепроверка сохранённого ответа и изменение контекста одного фрагмента. Никакой процент экономии до такого сравнения не заявляется.

## Поток и контракт доставки

Новые сущности проектируются новой миграцией: `CommentaryStream`, журнал неизменяемых пакетов/операций и версии реплик. Детальную раскладку таблиц выбирает разработчик; обязательны следующие инварианты.

- Поток связан с `job_id`, `match_id`, SHA256 исходника, длительностью, `context_hash`, версиями модели/промпта и поколением обработки. Чужой исходник, job или контекст отвергается до записи. У одной ещё не запечатанной попытки есть стабильный attempt_id, переживающий `--resume`; это не обещание изменять уже импортированный run_id. Генерация содержимого, writer_epoch разрешения и UUID итогового run различаются.
- У реплики стабильный `entry_id`, собственная revision, `start_ms/end_ms/anchor_ms`, текст, источники и статус `active/retracted`. Её ID не вычисляется из свободного текста или изменчивого ID итоговой reconciliation. Объединение соседних эпизодов сохраняет один ID, остальные явно отзываются; одинаковые слова сами по себе не причина объединения двух разных ударов.
- В локальном outbox пакет записывается атомарно **до** отправки. Он содержит `batch_id`, поколение, порядковый номер и операции upsert/retract/progress. Точный повтор возвращает прежний receipt; тот же ключ с другим телом — 409. ACK сохраняется локально; успешные окна из cache не оплачиваются заново при восстановлении доставки.
- Сервер выдаёт возрастающий `seq` принятой операции. Клиент читает изменения после последнего seq; потерянные ответы/перезагрузка страницы не теряют изменения и не дублируют строки. Начальный snapshot и его cursor согласованы транзакционно. Поздняя реплика может иметь старый таймкод, поэтому cursor строится по seq, не по времени эпизода.
- Пределы первого варианта: текст до 500 символов в API (220 — генерационный default), пакет до 64 КиБ/100 операций, поток до 5000 реплик; ссылки/диапазоны проверяются строгой схемой, текст выводится как текст без HTML. Превышение лимита даёт объяснимую остановку, не обрезание без сообщения.
- Для кабинета авторский выбор — запрос изменений примерно раз в 2 секунды, пока вкладка видима и обработка активна; ошибки дают backoff и ручной повтор. После терминального статуса выполняется последний catch-up. SSE можно добавить позже с тем же seq-контрактом, не делать его условием первого результата.
- `processed_frontier_ms` — непрерывно завершённый префикс, не максимальный таймкод ответа. Покрытые и неизвестные интервалы хранятся отдельно; обработанный фрагмент может не иметь реплик. Финальное состояние различает complete/partial/failed/cancelled; metadata содержит причину и фактический usage без ключей.

## Права и границы процесса

Обработчик не получает admin-cookie или постоянный администраторский ключ. Админ+ явно создаёт короткоживущее разрешение только на запись в конкретный частный поток; секрет передаётся отдельно от `job.zip`, не в URL/Git/архивах/логах, в БД хранится hash. По умолчанию срок 24 часа. Перевыдача разрешения сохраняет попытку обработки и её outbox, но увеличивает отдельный writer_epoch и отзывает старый token; это не новая генерация содержимого. Старый процесс не может дописывать после отмены/перезапуска/заморозки. Проверка разрешения выполняется и перед воспроизведением прежнего receipt. Вне loopback разрешены только HTTPS-адреса сервиса; сторонние перенаправления не используются.

Канал не позволяет читать другие матчи, публиковать результат, менять протокол, назначения, метрики, просить сервер скачать произвольный URL или запускать вычисления. При недоступной сети разрешён локальный режим: после восстановления отправляются те же сохранённые пакеты. Без подключения канала итог всё равно можно импортировать, но промежуточного просмотра в кабинете не будет.

Отмена/новая обработка создают отдельное поколение, не обнуляют старую историю. Подтверждение run и запись в поток сериализуются по match/stream lock; подтверждённый снимок не должен измениться от запоздавшего пакета. Отзыв роли/сессии закрывает частные чтения; все readers проверяют текущие права.

## Восстановление попытки, разрешения и запечатанного результата

Проверка документа отдельным разработчиком выявила две границы жизненного цикла; ниже зафиксированы решения автора на основе действующей неизменяемости импорта.

1. **Возобновление до запечатывания.** При временном сбое, потере сети или остановке по бюджету `--resume` продолжает тот же attempt_id, журнал/ID пакетов и cache. Продолжение платных запросов требует доступного явно разрешённого бюджета. Состояние partial/failed само по себе не делает изменяемым ранее экспортированный результат.
2. **Экспорт запечатывает снимок.** При сборке ZIP локально атомарно фиксируются финальные seq/digest и один result_run_id; повтор сборки/доставки этого снимка возвращает те же байты/UUID. После этого новые наблюдения не дописываются в него. Продолжение даже частичного результата создаёт новую попытку и новый run_id, независимо от того, успели импортировать первый пакет или нет. Подходящие CV/VLM cache-записи разрешено переиспользовать по прежним fingerprint; они не выдаются за новые API-вызовы.
3. **Сеть после экспорта.** Запечатывание не теряет недоставленные операции: outbox сначала догоняет сервер до финального seq, затем finalize проверяет digest и закрывает поток. Если ZIP импортирован раньше catch-up, импорт атомарно устанавливает тот же сгенерированный снимок и закрывает попытку; uploader получает явный sealed/imported receipt и прекращает дописывание, не применяет старый outbox поверх редакторских изменений. Несовпадение содержимого — конфликт, а не silent overwrite. Прежний run не переоткрывается.
4. **Обновление доступа.** Истечение/перевыдача token меняет только writer_epoch; attempt_id и тела batch сохраняются. Новое разрешение передаётся в заголовке, credential epoch не входит в хеш содержимого пакета. Новый разрешённый писатель может дослать тот же outbox и получить прежние ACK. Старый token отвергается до проверки idempotency. Подмена source/context или сознательный новый прогон создают новую попытку; её нельзя использовать для записи старых пакетов. Local workspace lock и серверный epoch вместе исключают двух действующих писателей.

Цена решений: после частичного экспортированного результата продолжение будет новой версией; интерфейс должен показывать её историю. Это сохраняет текущий контракт `run_id` → неизменяемое содержимое, вместо ослабления защиты импорта.

## Итоговый снимок и публикация

Контракт result v4 добавляет `commentary.json`, его schema_version, hash в manifest и ограниченные evidence по уже действующим правилам. v4 допускает независимые опциональные `understanding.json`/`events.json` по явным capability-флагам; старые правила обязательности v1–3 не переписываются. Лента и её evidence обязательны согласно флагу commentary, а при отсутствии evidence у пустой ленты не требуются фиктивные JPEG. Чистые валидаторы обмена не импортируют сервис, torch или сеть.

Финальный payload фиксирует реплики, источники, покрытие, source/context/model/prompt и sequence/digest локального потока. Сервис проверяет равенство доставленной финальной версии и пакета либо явно дополняет недоставленную историю из валидного пакета; расхождение нельзя незаметно заменить одним из вариантов. Для обработки без сетевого потока допустим импорт готового снимка с теми же проверками и приватностью. Импорт v4 повторяем и атомарен, файлы/БД откатываются при ошибке.

Ручные исправления существуют отдельными версиями поверх сгенерированного текста, не выдаются за ответ модели и не теряются при повторной доставке. В `AnalysisRun` хранится ссылка на собственный снимок/его revision; техническое подтверждение фиксирует разрешённые именованные ссылки. Изменение назначения после подтверждения требует существующего пути новой проверки. Имена в опубликованной реплике не подтягиваются из изменяемого справочника задним числом.

Публичный reader берёт ленту **только** у `Match.published_analysis_run_id` через общую проверку видимости турнира. Подмена stream/job/run ID, отсутствие публикации, draft/архив турнира дают 404. Частный API и статические артефакты не становятся публичными по наличию UUID. У старого результата без ленты честное отсутствие раздела. В публичном матче появляется «Текстовая трансляция» с пометкой «Автоматическое описание записи», таймкодами, пагинацией и ссылкой на видео только когда доступен реальный плеер/переход; частные кадры автоматически не открываются.

## Приёмка и проверка полезности

Техническая приёмка: реплики приходят в кабинет до окончания VLM-прохода и до импорта ZIP; обновление/отзыв строки, поздний ответ, reconnect, перезагрузка, точный повтор и изменённое тело, неизвестный диапазон, исчерпание бюджета, отозванный token/роль, старый процесс, новый run, неизменяемый опубликованный снимок. Дополнительно обязательны проверки отсутствия новых VLM-вызовов для совместимого кеша и повторного использования общего ответа, общий бюджет и запрет автоматического повтора при неизвестном исходе оплаты. Приватные данные проверяются прямыми guest/captain/admin URL. Протокол, капитанские подтверждения и метрики не меняются от реплик.

Проверка качества до широкого использования: размеченные непересекающиеся tune/control-фрагменты, среди них спокойная игра, атаки, остановки, гол/незасчитанный эпизод, плохо видимый мяч и номер. Оцениваем фактические ошибки реплик и приписанные личности, попадание времён, пропуски важных эпизодов, повторы, время первой строки после начала VLM, стоимость/минуту и время ручной коррекции. Порог публичного применения согласуется по результатам пилота; автоматическая публикация пилота не вводится. Русская связность не считается доказательством правильности события.

На синтетике проверяются контракты/доступ/восстановление, но не спортивная точность. Реальные платные запросы и отправка видео выполняются только в явно запущенном пилоте с указанным бюджетом; этот документ их не запускает. Видеозаписи, фото, ключи, веса и ZIP не добавляются в Git.

## Следующие направления, сохранённые из запроса

Общая хронология предоставляет основу для всех следующих задач, но первая текстовая поставка сама их не реализует:

- Чистое время, ауты/штрафные/начало/конец/гол: отдельные модели состояний, наблюдения и сопоставление с регламентом/протоколом; номера — лучшие кропы, несколько наблюдений и подтверждение капитаном.
- Хайлайты: синхронизация дополнительной трансляции/аудио, ASR с таймкодами, реакции и видеособытия, выбор границ/развязки и устранение повторов. Эмоциональный звук — сигнал выбора, не доказательство гола. Связь картинки камеры и трансляции пока не установлена, поэтому не является обязательным входом первой поставки.
- Озвучка готовой записи: текстовая лента → редактура → голос и синхронизированная звуковая дорожка. Источник фонового звука и отделение речи комментаторов требуется определить до этой стадии.
- Эфир: отдельная проверка задержки, ограничений будущего контекста, очереди/отмены реплик и изоляции генерируемого голоса от входящего анализа. Файловый проход не объявляется проверенным live-процессором.

## Решения автора для проверки пользователем

Сохраняем текущий доступ Админ+; отделяем попытку, epoch разрешения и запечатанный result_run_id; используем публикацию видеоанализа для публикации текста; первые строки появляются после CV-подготовки; основная шкала — видеозапись; по умолчанию короткие русские реплики; доставка с периодическим чтением, отдельным разрешением на один поток и поколением; новая версия ZIP v4. Для экономии предлагаем один совместный VLM-разбор, неперекрывающийся базовый проход с ограниченной памятью, основной клип без дублирующих общих JPEG, кропы по потребности, совместимый кеш и квоту адресных уточнений. Это решения автора в ответ на требование пользователя об экономичности; точные лимиты/стоимость и качество проверяются пилотом.
