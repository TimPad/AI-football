# Кабинет организатора — первый этап

Готовый локальный сервис: турниры и версии регламентов, общий справочник команд/игроков, заявки и снимки составов, календарь, ручной протокол и часы, документы, история, подтверждение и отдельная публикация.

Видео, S3, импорт Яндекс Диска/VK, импорт расписания, автоматические события и аналитический отчёт пока не подключены. Они остаются следующими этапами утверждённой спецификации. Существующий отчёт видео — отдельная часть проекта.

## Локальный запуск

Из корня репозитория, Python3.12 и Node24. Установите Docker Desktop и запустите его.

```sh
cp .env.example .env
# Заполните PGPASSWORD и тот же пароль в DATABASE_URL; файл не добавляется в Git.
chmod 600 .env
uv venv --python 3.12
uv pip install --python .venv/bin/python -e '.[dev,web,web-dev]'
docker compose up -d db
.venv/bin/alembic upgrade head
.venv/bin/python -m aifootball.service.auth.cli create-admin --login admin
npm --prefix web ci
npm --prefix web run build
.venv/bin/python -m uvicorn aifootball.service.app:create_app --factory --host 127.0.0.1 --port 8000
```

CLI запросит пароль дважды; минимум12символов. Пароль не передаётся в аргументах команд и не печатается в чате. На текущем компьютере администратор уже создан, его данные лежат в приватном `data/service/admin-password.txt`. Демонстрационный турнир и команды имеют явную метку «Демо».

Откройте <http://127.0.0.1:8000/tournaments>. Если интерфейс ещё не собран, сервис показывает команду сборки; API продолжает работать.

Настройки `.env`:

- `PGUSER=aifootball`, `PGDATABASE=aifootball`, `PGPASSWORD` — локальный PostgreSQL в Docker; порт хоста54329.
- `DATABASE_URL=postgresql+psycopg://aifootball:YOUR_URL_ENCODED_PASSWORD@127.0.0.1:54329/aifootball`. Пароль URL-кодируется, если содержит специальные символы.
- `ALLOWED_ORIGIN=http://127.0.0.1:8000` — точное происхождение браузера, проверяется при входе и изменениях.
- `SECURE_COOKIES=false` — только локальный HTTP. Для размещения с HTTPS: `true`, соответствующий Origin и приватный доступ к БД.
- `SESSION_HOURS=12`, `ATTACHMENT_ROOT=data/service/attachments`.

База хранится в Docker volume `service_pg`. Перезапуск приложения или `docker compose restart db` сохраняет данные. Не удаляйте volume. Документы лежат отдельно от БД и не раздаются как статические файлы.

Для разработки запустите API на8000 и `npm --prefix web run dev`; Vite проксирует `/api` на8000. Установите `ALLOWED_ORIGIN=http://127.0.0.1:5173` и перезапустите API; входите через5173. Порт Vite должен совпадать с Origin, поэтому при занятом5173 освободите его или задайте одинаковый порт/Origin.

`GET /api/v1/health` проверяет процесс, `/api/v1/ready` — подключение к БД и соответствие текущей миграции. Без БД или с устаревшей схемой readiness возвращает503. Миграции и `web/dist` располагаются рядом с кодом в полной копии репозитория.

## Работа с матчем

Создайте турнир → сохраните регламент → добавьте команды из справочника → заполните заявки и номера → создайте матч → выберите составы.

Все параметры регламента редактируются. Сохранение создаёт новую неизменяемую версию. Старые матчи сохраняют прежний регламент; применение к будущим матчам требует выбора и предпросмотра. Исключение для одного матча записывается с причиной.

Протокол можно заполнять во время или после матча. Пустое значение счёта/фолов/карточек/времени означает «неизвестно»; ноль вводится явно. Известные события и сообщённые итоги хранятся отдельно. Гол с пенальти записывается связанным эпизодом; серия пенальти не прибавляется к игровому счёту. У автогола команда события — команда автора, гол засчитывается сопернику.

Часы ручные; источник не является табло или видео. Для чистого/смешанного времени доступна пауза по регламенту. Тайм заканчивается явным действием; достижение00:00 не завершает его автоматически. Коррекция времени требует причины. Изменение часов и границы таймов видны в истории.

Завершите матч, укажите известный итог и подтвердите протокол. При пропусках явно подтвердите неполноту. Подтверждение создаёт снимок; публикация выбранной версии — отдельная кнопка. Повторное открытие для исправлений сохраняет предыдущую публичную версию до новой публикации. Снять публикацию можно отдельно. Публичный URL показывает только выбранный ручной протокол; внутренние заметки и документы не доступны гостю.

При потере сети правка остаётся в очереди. Попытка повторяется с тем же ключом, телом и ревизией. При конфликте автоматическое изменение останавливается: сравните локальный ввод с сервером, примените как новое изменение либо скачайте и отбросьте локальную правку. Ошибка422 сохраняет очередь/форму для исправления; сначала скачайте и уберите ошибочную команду, затем отправьте исправленный ввод. При истечении сессии войдите тем же администратором; ввод сохраняется в этом браузере.

Локальные черновики не содержат cookies/паролей. Не используйте общий браузер для приватного ввода: после выхода сохранённые черновики скрыты, но остаются на диске браузера для восстановления. При отказе localStorage интерфейс сообщает, что копия остаётся только в памяти, и предлагает JSON. Повреждённые копии не отправляются автоматически. Для нескольких окон есть блокировка владельца с15секундной арендой и явная передача управления; окончательную защиту обеспечивают серверные ревизии и ключи команд.

Документы: PDF/PNG/JPEG до20МБ, проверка сигнатуры и MIME, приватное скачивание. Файл не сохраняется в браузерном черновике. Если ответ загрузки потерян, повторно выберите тот же файл: ключ и ревизия загрузки сохраняются. Изменённый файл под прежним ключом сервер отклонит.

## Проверки

```sh
.venv/bin/python -m pytest -q --tb=short
npm --prefix web test
npm --prefix web run build
web/node_modules/.bin/playwright install chromium
npm --prefix web run test:e2e
```

Backend-тесты используют отдельные `aifootball_test` и `aifootball_migration_test`. Сквозные тесты поднимают сервис на8181 с отдельной БД `aifootball_e2e` и тестовым администратором. Организаторская БД не очищается. Сценарии создают записи с уникальными именами; тестовые БД можно удалить отдельно после проверки. Порт8181 должен быть свободен. После изменения контрактов:

```sh
.venv/bin/python scripts/export_service_openapi.py --output data/service/openapi.json
npm --prefix web run types:api
```

## Резервная копия и восстановление

Остановите запись новых матчей и документов на время согласованной копии; PostgreSQL dump и архив документов должны соответствовать одному состоянию сервиса. Не удаляйте документы, которые вошли в подтверждённые версии.

Для локального Docker запустите:

```sh
.venv/bin/python scripts/verify_service_backup.py
```

Команда создаёт приватные `database.dump` и `attachments.tar.gz` в `data/service/backups/<UTC-time>`, восстанавливает их в новую `aifootball_restore_<uuid>_test` и отдельную папку, сверяет количество записей, точные снимки, указатели публикаций и SHA256 документов. Исходная БД и документы не изменяются. Верификацию наполненного тестового сценария можно выполнить с `--source e2e`; это использует отдельную E2E-базу и её документы. Тестовая восстановленная БД сохраняется для ручного осмотра. Копии содержат приватные данные; переносите их только в закрытое хранилище.

Для штатного восстановления используйте чистую новую БД, `pg_restore --exit-on-error --no-owner` из PostgreSQL16, распакуйте архив в приватный `ATTACHMENT_ROOT`, задайте новый `DATABASE_URL` и сначала проверьте `/ready`, матч, опубликованный снимок и скачивание документа. Не восстанавливайте поверх рабочей БД.

Внешнее размещение, домен, облачные ключи и S3 этим этапом не настроены.
