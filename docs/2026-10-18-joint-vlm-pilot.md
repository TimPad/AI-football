# Пилот единого VLM-разбора

18 октября 2026. Эксперимент выполнен в `codex/tournament-captain-ux` по просьбе пользователя «попробуем и протестируем». Это отдельный локальный проверочный путь; автоматическая лента в кабинете, доставка во время обработки и ZIP v4 ещё не реализованы.

**Результат:** новый медиавход заметно дешевле на сопоставимом окне, кеш и запрет повторов работают. Качества распознавания пока недостаточно для достоверной автоматической трансляции. Проверка структуры ответа не устанавливает истинность описания.

## Что проверялось

`scripts/verify_joint_vlm.py` использует `understanding/pilot.py` и существующий Qwen-клиент. Один запрос получает видеоклип, до двух отобранных кропов номеров, компактные подсказки трекинга, реальные измерения скорости/размеров поля и ограниченную память. Общие JPEG из клипа повторно не отправляются. Одним ответом запрашиваются события, состояния, фазы, номера, реплики и кандидаты хайлайтов. Счёт/UUID/судейские решения модель не устанавливает.

Три заранее выбранных фрагмента: Ярославль 6–42 с первого исходника, Ярославль 6–42 с другого исходника и Кострома 12–36 с. Всего 96 секунд, восемь неперекрывающихся 12-секундных окон с выравниванием по кадрам. В Костроме есть звук; отдельного ASR и синхронизации другой трансляции нет. Ручные метки касаний/остановок используются только при оценке, в запросы не попадают.

Исходный режим взят из ранее оплаченного локального кеша Qwen на том же видео. Кеш-файлы с одинаковым provider request_id считаются одним ответом. Повторных платных baseline-запросов нет. Сравнение историческое, модель используется по имени, поэтому это не рандомизированный A/B-тест. Для целого участка старый план содержит пять перекрывающихся окон, новый — три последовательных; сравнивать суммарные расходы как эффект одного изменения нельзя.

## Расход и повторное использование

На одинаковом первом интервале **6041–17989 мс**, с теми же 7310 video tokens:

| Режим | Входные токены | Выходные токены |
|---|---:|---:|
| Сохранённый прежний ответ | 27 991 | 1 755 |
| Единый пилотный ответ | 10 318 | 554 |

Входных токенов на этом окне меньше на **63,1%**. Изменились одновременно формат медиавхода, объём контекста и контракт ответа; это не доказательство сохранения качества и не обещание такой экономии на полном матче.

Журнал всего пилота:

- Восемь запросов, восемь различных ключей эффективного входа; автоматических повторов не было.
- Для семи завершённых ответов известен usage: **70 255 входных / 3 718 выходных токенов**. Один из них вернул `[]` вместо объекта; известный расход всё равно сохранён.
- Один ранний ответ не сохранился до ошибки `response_json`. Его расход неизвестен, удержан резерв **25 000 / 4096**. Этот резерв не выдаётся за фактическое списание, ответ повторно не запрашивался.
- Полный `--cache-only --continue-unavailable` заново прошёл все окна: **ноль новых запросов**, бюджет остался на восьми. Шесть JSON-объектов использованы из кеша; два недоступных окна не отправлялись повторно.

Лимиты пилота: восемь вызовов, бюджетный порог 200 000 входных токенов по оценкам/usage и 32 768 выходных; до вызова резервируются 25 000 входных и 4096 выходных. Оценка медиатокенов не является серверным ограничением входа. Потерянный ответ сохраняет резерв. Увеличение лимитов автоматически не выполнялось.

Для ориентира, по опубликованному стандартному тарифу Singapore на дату проверки (1,094 CNY/миллион входных и 3,427 CNY/миллион выходных) известная часть оценивается в **0,0896 CNY**, резерв неизвестной — ещё **0,0414 CNY**. Это расчёт по usage и тарифу, не выписка счёта; скидки/окончательное списание не проверялись. [Тариф поставщика](https://help.aliyun.com/zh/model-studio/model-pricing).

## Качество и ограничения

| Фрагмент | Строго валидные ответы | После локальных правок | Сохранённые реплики |
|---|---:|---:|---:|
| Ярославль, первый | 1/3 | 2/3 | 2 |
| Ярославль, контрольный | 1/3 | 2/3 | 4 |
| Кострома со звуком | 0/2 | 2/2 | 4 |

Локальная проекция не меняет исходный ответ: восстанавливает только отсутствующую версию/базу времени из контракта запроса, заменяет `unknown` на `null` в полях стороны/владения, удаляет реплики без ссылок. Удалены три такие реплики. Оставшаяся проекция полностью проходит тот же валидатор. Никаких новых событий, evidence-ссылок, исправлений номеров или времён код не придумывает. Всего доступно шесть структурированных объектов, десять реплик, четыре события-кандидата и два кандидата хайлайтов.

Проблемы содержания существеннее формата:

- В первом Ярославле на 30-й секунде модель пишет про начало матча с центра и «жёлто-синих» соперников; на записи продолжается игра зелёных против оранжевых. Ссылки и схема при этом валидны.
- В контрольном Ярославле оба доступных окна размечены как `playing` на всём протяжении. Из восьми ручных меток внутри этих окон шесть совпали, две метки `dead` ошибочно названы игрой. Первое окно с дополнительными метками недоступно; эти восемь точек не описывают качество всего контрольного отрезка.
- В двух доступных окнах первого Ярославля совпали восемь меток игры, но окно с известной остановкой недоступно. Это не подтверждение правильного определения остановок и не улучшение чистого времени.
- Кандидат удара в Костроме сопровождается собственным ограничением модели «удар не был зафиксирован камерой»: движение к воротам нельзя считать доказательством удара. Два прочитанных номера не имеют независимой размеченной выборки для оценки точности.

Пилот показывает экономию медиавхода и возможность использовать один ответ несколькими функциями. Следующая гипотеза: сохранить общий проход, отделить краткие наблюдения от свободного рассказа, формировать часть реплик кодом из конкретных событий, проверять основание остановки/удара и передавать релевантный контекст мяча, когда он действительно рассчитан. Для следующего платного сравнения нужны отдельные размеченные интервалы событий и новый явно заданный бюджет. Текущий пилот не автоматически публикуется.

## Проверки и воспроизведение

Пройдено **237 тестов** обработки, понимания матча, Qwen и пилота, без реального API и рабочей БД. Новые сценарии проверены RED → GREEN: кеш после перезапуска, конкурентный запрос, лимит, crash после reservation/receipt/wire, запрет повтора неизвестного исхода, сохранение завершённого ответа до JSON parsing, локальные правки без изменения raw, отсутствие чужих по времени CV-подсказок, безопасное отображение повреждённого ответа. Отдельный read-only reviewer проверил изменения и исправления двух найденных дефектов.

Локальный HTML-отчёт проверен в браузере; все восемь видеоклипов доступны. Итоговые JSON, usage-аудит, исходные ответы, кадры и логи лежат в игнорируемой папке `output/joint-vlm-pilot-2026-10-18/`. Реальные записи и ключи в Git не добавлялись.

Создайте локальный manifest вне Git с `cases`: `id`, абсолютные `video`/`artifacts`, `start_ms`/`end_ms`, необязательные `labels` и `split`. Артефакты должны относиться к этой записи и содержать `tracks.parquet`, `state.parquet`, `metrics.json`, `meta.json`. Необязательный `baseline` задаёт `case_id`, ранее сохранённый `result.zip` и папку его `cache`.

```sh
# Подготовка медиа без API
.venv/bin/python scripts/verify_joint_vlm.py --manifest output/pilot/manifest.json --output output/pilot
# Явный запуск в фиксированном бюджете; продолжение других окон без повтора недоступного
.venv/bin/python scripts/verify_joint_vlm.py --manifest output/pilot/manifest.json --output output/pilot --apply --continue-unavailable
# Повторная проверка уже оплаченных ответов: сеть запрещена
.venv/bin/python scripts/verify_joint_vlm.py --manifest output/pilot/manifest.json --output output/pilot --cache-only --continue-unavailable
```

Код возврата 2 при невалидных/недоступных ответах сохраняется даже после удачной локальной проекции: строгая приёмка модели не подменяется исправленным выводом. Обычный `process-job` этот экспериментальный режим не включает. Новый необязательный `response_sink` у клиента Qwen только позволяет пилоту сохранить завершённый текст/usage до JSON parsing; без него поведение прежнее.
